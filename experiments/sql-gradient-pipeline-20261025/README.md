# 有界 32 槽 CPU 接收队列

**结论：槽等待从约 17.5 秒降到约 0.03 秒，但第 2/3 轮 107.01/110.11 秒与原配置接近，单这一项不宣称加速；它与原生归约事件阈值 2→4 组合后，才成为选中的 101.2831 秒/256 条方案。**

## 背景

上一轮 [双缓冲 CPU 累积](../sql-gradient-cpu-20261025/README.md) 已证实在 `micro16 × 累积8` 下两个接收槽不够：主线程每轮约 17.5 秒等槽、边界另约 9.8 秒。本轮只扩大接收队列，不改通信、累加顺序与 Adam 数学。

## 配置

双卡物理 2/3，global256、每卡 micro16、累积 8，BF16 计算与累积、CPU FP32 master/m/v，24 线程/rank 与 NUMA 绑核均与上一轮相同。

## 做法

- 30 个 128 MiB 小槽 + 2 个最大分片槽，共 32 槽，每 rank 约 6.12 GiB 锁页 CPU 内存。
- 单个 FIFO worker 保证同一参数的相加次序不变。
- 选择槽时先取“容量够且已空闲”的最小槽，否则按提交顺序回收最早的槽。

## 结果

| 项目 | 结果 |
|---|---|
| tiny 三更新 + 逐位比对 | 通过（复用 `sql-gradient-cache-20261025/tiny-native` 参考） |
| 主线程槽等待 | 约 17.5 秒 → 约 0.03 秒 |
| 第 2/3 轮 | 107.01 / 110.11 秒 |
| 与阈值 2→4 组合后 | 101.2831 秒/256 条（−6.19%） |

## 状态

- 单独使用：**已否决**（与原配置接近，不能证明加速）。
- 作为选中组合的一部分：**已采用**，正式结论与重放入口在 [sql-reduce-schedule-20261025](../sql-reduce-schedule-20261025/README.md)。
- 收尾：队列容量提升不等于关键路径变短——CPU 相加、边界交接与通信仍在同一路径上，这一点在后续几轮反复被验证。
