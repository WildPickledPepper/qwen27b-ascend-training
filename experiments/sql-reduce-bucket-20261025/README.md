# 超桶大梯度：就绪即发送（整模型未获益，不采用）

基于95.74秒/256条配置，保持256/16/8、原768条数据顺序、padding、BF16计算累积、FP32通信及CPU FP32主权重/Adam。大小分布和源码见[研究记录](../../research/gradient-ready-scheduling-20261025.md)。本实验名中的bucket指触发发送时机，**没有扩大桶**。

原生在下一参数回调中才刷新前一超桶大参数。候选对这些原本就必定单发的参数立即调用同一原生归约函数，保持包分组和参数顺序，争取与下一段梯度计算重叠。保护检查确保桶确实只含当前大参数；共享安装和模型文件不改。

原生/候选tiny均使用4096元素桶，强制覆盖改动分支；两rank三次更新、8微批的完整梯度/master/m/v逐位一致后才执行27B。tiny每轮16次归约，候选每轮16次立即刷新，确认改动实际被覆盖。

## 实测结果与决定

整模型前3更新相同768条，首轮冷启动排除，末轮重复首256仅采样；后两轮按较慢rank取均值。事先设定至少比95.74秒快1%、同768条验证一致且工作量审计通过才更新配置。本轮94.8594、99.0913秒，平均**96.9753秒/256条**，比参考95.7402秒慢**1.29%**，因此**不采用，继续保留95.74秒配置**。不从两轮里挑较快的一轮宣称成功。

每轮实际2960次大参数立即刷新。通信大小/类型/次数完整分布与原配置一致，仍4504次ReduceScatter、4721次AllGather；计算任务仍219114。每rank逻辑梯度复制295.86GB、BF16累积、FP32通信和master/m/v字节不变。768条后同8验证loss0.8581519723、204/224正确token，与原配置一致；不代表整模型长期逐位或质量证明。

## 为什么没有采用

同一第4轮输入与padding、同rank0 Level1/Db采样：

| 指标 | 95.74秒配置 | 提前发送候选 |
|---|---:|---:|
| 设备窗口 | 113.48秒 | 113.60秒 |
| ReduceScatter累计 | 24.96秒 | 25.15秒 |
| ReduceScatter与计算重叠 | 11.59秒 | 9.87秒 |
| ReduceScatter未与计算重叠 | 13.36秒 | 15.28秒 |
| AllGather未与计算重叠 | 9.10秒 | 9.33秒 |

代码中的发送触发点确实提前，设备上与计算的重叠却没有改善。这个结果说明单独前移大包发送不能自动改善整条流水；本轮不按“源码看上去更早”判断加速，也未证明哪一种具体设备竞争机制导致变化。

无采样rank0前向范围平均16.91→18.96秒，反向64.21→63.38秒，step14.61→14.63秒。第三轮前向20.86秒（参考17.07秒）是实测回退，但该轮未采样，不能用第4轮的时序冒充这3.79秒的硬件根因。已知的是本轮整模型不更快，而非已经完全解释所有波动。

## 排除两个看似可改的方向

- 原配置1416次小count通信合计约0.094秒，小包启动不是13秒暴露时间的主要来源。
- 将后台接收线程排除后，原配置归约主线程内事件同步只有14次、累计0.346秒；候选8次、0.334秒。因此没有继续盲目扩大归约事件队列。总CANN事件等待不能直接等同主线程背压。

候选末轮仅8次物理显存分配API、累计约0.0013秒，没有重现历史12GiB驻留方案的大规模物理页热点；此观察不用于解释未采样的第三轮。尝试直接按connectionId关联CANN与通信起始时间得到零匹配，未据此推断队列时延为零或提前了多少。
