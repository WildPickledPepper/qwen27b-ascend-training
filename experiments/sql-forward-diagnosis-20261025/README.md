# 前向增加定位：异常集中到首微批，两次复现未重现额外4秒

结论：历史约4秒增加集中在第三轮第一个微批；详细采样和轻量计数两次复现均未重现该长停顿。**尚未定位历史停顿的具体根因，也没有证据认定CPU融合导致固定前向退化。** 不修改原95.74秒默认，不据诊断测试挑选最快成绩。

## 先读历史记录

三次既有运行的数据顺序、长度及padding相同。rank0第三轮如下：

| 指标 | 原参考 | 归约候选 | CPU融合候选 |
|---|---:|---:|---:|
| 首微批墙钟（含前向/反向） | 8.957秒 | 12.586秒 | 12.811秒 |
| 全轮前向宿主范围 | 17.074秒 | 20.859秒 | 21.097秒 |

额外时间几乎集中在首微批，其他微批近似正常。两个不同候选都出现过，两rank都受影响；不能由此确定慢的起点或因果方向。第三轮首微批rank0补齐长度256，但首轮已运行该长度，不把“首次遇到新长度”当成根因。其他JIT key仍不能据此排除。

“前向范围”包括输入构造/回传、模型调用、loss缩放和读取loss时的设备等待，并不是纯矩阵乘时间。

## 定向复现一：第三轮Insight数据库与CPU调用记录

同CPU融合版、global256/micro16/累积8、原768条训练，保留原验证-after2行为。第三轮rank0 Level1/Db；首微批两rank加cProfile，各微批记录batch、engine、loss读取、allocated/reserved和宿主缺页/切换信息。代码只增加观测，不改数学、精度或共享安装。

目标首微批rank0：batch **0.0061秒**，engine **3.7163秒**，loss缩放/读取 **0.0319秒**；含Level1与cProfile开销，不能当正常速度，也不能把与后续微批之差全部解释为采样开销。CPU调用记录没有捕获到原先额外4秒的长阻塞。

通过ascend-profiler-db-explorer既有CTE和只读SQLite校验Profiler正常停止、Db导出及时间窗口。记录的第三轮112.6419秒，对应设备窗口112.6671秒。自定义scope按文档中的ns时间戳关联宿主API，结果：

- 首次目标engine范围内，最长同步`aclrtSynchronizeStream`约58.58毫秒。
- 整个第三轮只有一次`aclrtMallocPhysical`，约0.119毫秒；没有在这次正常复现中看到数秒物理分配。
- API按时间相交统计，不冒充宿主到设备的精确依赖映射；嵌套耗时不能相加。

这次正常复现不覆盖历史异常现场，不能据此断言历史分配、编译或同步一定没有问题。

## 定向复现二：原路径加轻量allocator/GC计数

保留原训练路径和同样的验证行为，关闭详细Profiler/cProfile，仅记录前向分项、NPU allocator重试/OOM计数、Python各代GC耗时。依次完成前三轮，未与第一项并占设备。

rank0第三轮全前向 **17.4911秒**，接近原参考17.0739秒，而非此前21.0970秒。rank0显存reserved在目标前向增加240MiB，但没有重试或长停顿；因此不能只凭reserved增加就归因4秒。两rank观察到的较长gen2 GC均约0.35秒，没有捕获4秒GC。

## 数值、失败与资源

两次原始训练样本哈希/顺序/长度、验证划分、256/16/8配置、CPU融合扩展及FP32状态设置均核对。详细版768条验证与原版完全一致。轻量版仍204/224正确token，但loss为0.858151912689209，对原0.8581519722938538差−5.960464477539063e−8（约一个该数值的FP32 ULP）。严格相等检查捕获了差异，报告保留`same_validation_at_768=false`和实际差值，没有将它改写成逐位一致，也未归因为特定机制。这两次诊断不构成长训练质量证明。

首次后处理在训练子进程尚未退出时被控制器完成状态保护拒绝，等待正常退出后再导出；没有绕过资源保护或重启训练。轻量导出最初被严格loss相等检查拒绝，随后改为明确导出精确相等标志和实际差值；未把差异隐藏为通过。

全部任务正常退出，两次均核对2/3卡无进程，其他既有服务仍在；原权重只读，没有保存新整模型checkpoint，不改默认配置。首次历史定位已单独提交；本阶段源代码与过滤证据按持续授权提交。
