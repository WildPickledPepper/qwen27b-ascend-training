# Qwen3.5-27B纯文本SQL训练速度对照

2026-10-25用户授权按公开Text2SQL任务对照双910B2。原始Qwen3.5-27B已在服务器，使用同一基础模型系列，不沿用上一轮Qwen3.8 checkpoint。已完成3次完整更新、数值和配置审计；2/3卡均已释放，无新完整checkpoint。

## 实测结果

| 项目 | 我们双910B2 | 作者16张H200 |
|---|---:|---:|
| 全局样本/更新 | 256 | 256 |
| 长度上限 | 512 | 512 |
| 每256样本耗时 | **191.47秒**，后2轮实测均值 | **约16.05秒**，公布总时间折算 |
| 整机样本/秒 | **1.3370** | **约15.9498** |
| 17.8万样本一遍 | **约36.98小时**，仅稳态训练外推 | **3小时6分**，作者公布 |

公开整机吞吐约为我们的11.93倍，卡数为8倍。按卡数简单归一的吞吐比为1.49，但这不是独立单卡实测，也不能排除实际长度分布、框架和调度差异。我们的外推不包含全部数据准备、编译、验证和保存，不是完整epoch实测时间。

三轮实测为246.7943（冷）、191.9239、191.0218秒。后两轮每步实际输入28549/28564 token，padding后47104/47616位置；有效输入约149.14 token/s。保留token口径以供复核，主比较使用同256样本的时间。全部参数及FP32状态审计通过；全局m/v总215,167,987,712字节。分配峰值每卡约39.14 GiB，未声称这是双卡速度上限。

8条SQL验证、224个回答token：loss1.010828→0.850936，正确token202→204。仅3次更新，其中首步lr=0用于预热，后两步非零；不能当作完成SQL训练或长期质量对照。新组从原checkpoint开始，未沿用容量检查后的权重。

宿主计时中，后两轮前向约32.5–33.2秒、反向约144–145秒、step约14.3–14.5秒；CPUAdam本体约9.5–10.1秒/卡。反向范围含梯度同步、CPU卸载和等待，不能当纯NPU反向计算时间；本轮未额外采完整Profiler来拆分它。

## 参考任务与对齐项

[作者模型卡](https://huggingface.co/mahernaija/Qwen3.5-27B-Text2SQL)报告16×H200、FSDP、BF16全参文本训练，sql-create-context约78K加Gretel约100K，1 epoch，3小时6分钟。全局batch256、每GPU micro2、累积8、长度上限512。视觉编码器未训练。

进一步核对作者checkpoint-698中的trainer_state.json和training_args.bin：698次更新，seed42、AdamW lr2e-5、betas=(0.9,0.999)、eps1e-8、weight_decay0.01、max_grad_norm1、cosine调度及5%预热。training_args仅通过zip/pickletools检查原始opcode中的标量，不反序列化执行远程pickle。文件版本和SHA256存入数据来源清单。

本实验：

- 仅实时空闲、已授权的物理2/3号910B2；原始权重只读。
- Qwen3.5-27B文本主干26,895,998,464参数，BF16计算、CPU FP32 master/m/v、标准双进程ZeRO-3及既有锁页回传流水。
- 全局batch256；正式计时每rank micro8、累积16。先用micro4/累积32完成一轮容量检查，首轮约400.63秒含首次执行和优化器冷状态，不计稳态成绩；依据每卡分配峰值约38.48 GiB提高microbatch。作者16张卡可容纳的每卡batch不限制我们使用更合适的microbatch；保持每次更新总样本数一致。
- 长度上限512，按微批量最长样本向64倍数补齐（至少128），保留SQL回答标签，屏蔽prompt/padding。
- 作者未公开完整预处理代码。按模型卡描述手工chat、不注入think、去除INSERT；按schema+question去重，排除Gretel官方test重叠，不使用GSM8K。不能称作者精确数据管线复现。
- 从混合训练集确定性打乱选768条，分3次完整更新，不重复样本；8条独立SQL验证。首步预热，后2步作短跑速度，完整一遍仅外推，不默认跑17.8万条。
- 采用作者AdamW主要超参和698步调度；首步lr=0与预热一致，后续步非零。保留我们容量所需的激活重算和融合实现差异。
- 扩展先前GDN适配的长度保护到512；原始VeOmni实现不改，先在2/4批量、512长度下与HF参考做前后向FP64误差核对，再启动整模型。

## 速度比较方法

最终优先展示“学习256条要多少秒”和“每秒多少样本”。作者总时长11160秒、数据量约178000条，平均约15.95样本/秒，折合256条约16.05秒；这是全流程总时间折算，不是作者稳态实测步耗时。其698步也仅对应约16秒/步，数据量的整数舍入及末步处理会有差异。

我们的短跑取两rank较慢时间，排除首步，同时记录有效输入token、padding位置、loss、FP32状态字节和显存峰值。短跑训练时间外推不包含启动、全部验证和保存；不能称完整epoch真实总耗时。分别报告16卡对2卡的整机速度比与除以卡数后的吞吐，后者不假定线性扩展，也不冒充单卡独立实测。

## 文件

`fetch_public_data.py`下载固定版本公开文件及作者配置标量；原始数据仅存忽略的datasets目录或远端raw目录。`prepare_data.py`执行可追溯处理；`build_entry.py`从已验证的融合入口生成独立训练代码；`run_benchmark.py`依序做数据、512数值检查和3步训练，并保留失败。`summarize.py`只输出聚合指标、哈希和配置，不导出数据全文、权重或服务器路径。

本轮不修改共享库、原模型或其他任务，不生成完整训练后checkpoint，不自动Git提交推送。

## 容量检查后的执行调整

首个保守micro4组完成整次256条更新后，由`run_matched.py`只向已记录且进程组核对通过的本任务torchrun发送TERM，等待2/3卡释放，再从原checkpoint重新加载micro8正式组。首组按主动结束的容量检查保留，不当作三步成功训练；新组仍从原权重、相同768条数据开始。没有把改变microbatch前后的参数轨迹混在一起。

处理后的完整混合训练集原始长度P99=200、最大470；作者仅描述其P99=373，未公开处理脚本。因此任务对齐到同基础模型、数据来源、长度上限和全局批量，样本次序与实际长度分布未证实完全一致。作者框架的参数分组与我们的单组AdamW也未逐项复现；本结果衡量当前双卡方案，不能解释为纯硬件性能比。
