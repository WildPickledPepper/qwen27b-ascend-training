# 压缩FFN权重，将空间分给梯度累积

2026-10-26用户授权把已验证BF16无损压缩接入训练，用释放的HBM扩大梯度累积，实测净速度。只在实时空闲物理2/3卡独立实现，原81.22秒入口、原checkpoint和其他任务不动。

固定原768条/顺序/长度/padding、global256/micro16/16流水线micro、48层选择性重算、BF16计算与保序梯度累积、CPU FP32 master/m/v、相同全局裁剪/Adam/学习率/更新边界。

## 先集成FFN，避免一次改变所有模块

每卡96个FFN gate/up/down矩阵，原BF16 15.9375GiB，压缩约11.9GiB。只替换这部分存储，GDN、普通attention和embedding/lm_head保持原生权重。初始从已逐帧验证的归档读取；所有载入矩阵再次在NPU按int16位型与当前原生权重完整比较，随后释放原矩阵存储。

实际初始化：2卡原FFN17,112,760,320 bytes，带guard payload12,823,577,408 bytes；框架allocated26,896,201,728→22,607,050,240 bytes。3卡payload12,776,564,704 bytes，allocated26,896,212,480→22,560,044,032 bytes。释放的是实际NPU存储，不把离线压缩率冒充线上显存下降。元数据和校验guard已计入payload，解压/校验workspace仍需另计。

将梯度驻留4→7GiB，剩余约1GiB空间用于解码矩阵、workspace和checkpoint重算的临时权重，正式峰值见下方实测。全部权重归档总共省12.63GiB并不意味着本次每卡增加6GiB：本次只采用FFN子集。

## 原生算子与autograd

每个FFN Linear前解码原BF16矩阵，调用原生Linear，结束后换成保留原形状的零步长元数据占位，不让完整权重持续驻留。非checkpoint部分通过`saved_tensors_hooks`保存权重的记录编号、形状/stride/offset，反向需要时解码重建视图，避免autograd把原矩阵留住。checkpoint内层hook仍遵循原框架机制，重算时同样调用模块解码；退出/提前停止重算也释放权重。

仅在原全局更新边界，CPU FP32 Adam按原顺序更新master，原样转换BF16分块后传回NPU，重新编码并逐位验证；作者codec位差/膨胀即原字节回退。没有量化权重、梯度、主权重或m/v，没有提前更新、改写matmul/反向求和顺序，也没有运行时从CPU取旧计算权重。

作者BF16 kernel复用已验证静态库；只链接宿主桥，解码提交到当前PyTorch流、不逐帧额外同步。编码读取Header/字节验证保留必要同步，其全部开销纳入训练整步。

依据[PyTorch 2.10 saved_tensors_hooks文档](https://docs.pytorch.org/docs/2.10/autograd.html#torch.autograd.graph.saved_tensors_hooks)，未压缩Tensor的pass-through返回detach以避免图引用环。tiny首次完整状态门槛通过后补上这一不改变值的引用处理；额外CPU autograd检查与正式源代码哈希分别归档，不能说该行已包含在首次tiny源码里。

## 实测结果：能装下，但本实现不采用

固定256条一轮，第二、三轮不带采样：88.9638 / 89.1225秒，均值 **89.0431秒**。原4GiB驻留版本80.2020 / 82.2300秒，均值 **81.2160秒**。本轮耗时增加 **9.64%**，保留81.22秒版本。第四轮带Profiler，仅作诊断，不参与速度均值。

| 项目 | 原4GiB缓存 | 压缩FFN + 7GiB缓存 |
| --- | ---: | ---: |
| 每轮256条耗时 | 81.22秒 | 89.04秒 |
| 每卡梯度驻留 | 4GiB、29个参数 | 7GiB、47个参数 |
| rank0 CPU梯度相加累计 | 47.23秒 | 42.30秒 |
| rank0主线程等接收槽累计 | 32.82秒 | 17.85秒 |
| rank0前反向及收尾 | 63.37秒 | 67.64秒 |
| rank0全局范数 | 1.42秒 | 1.42秒 |
| rank0更新及回传尾部 | 16.43秒 | 19.98秒 |
| 两卡allocated峰值 | 56.56 / 54.05GiB | 56.25 / 53.33GiB |

CPU相加、槽等待是线程内部计时，与设备执行互相重叠，不能与整步阶段直接相加。上表阶段使用正常两轮均值；整步取较慢rank，因此小数有微差。

每卡实际梯度D2H从365.91GB降到317.59GB，少48,318,382,080字节/轮；额外3GiB完整参数梯度保序相加16次后只传一次。初始化实际allocated减少约3.99/4.04GiB，并把其中3GiB用于梯度缓存，保留临时解码空间。7GiB正常完成，无OOM。这证明“把省下显存分给累积”兑现了，但不是净加速。

## ms证据：CPU减负被新增设备工作抵消

使用ascend-profiler-db-explorer技能的原始compute/comm CTE，通过只读SQLite分析双rank第四轮DB；SQL与过滤结果保存在证据JSON，不靠前端截图。

rank0采样窗口87.09→93.80秒，互斥覆盖分解：计算39.56→45.81秒；无计算重叠的通信7.28→6.80秒；扣除计算/通信后的复制14.12→20.75秒；其余26.13→20.45秒。CPU等待空间下降，但新增计算与复制超过了省下的等待。

新增工作可以直接在设备算子表看到：

- BF16解压`decompBF16`：9376次，累计2.535秒。前向、重算、反向均可能需要完整原矩阵，不能拿离线一次解压时间当整轮成本。
- 每次更新后的逐位检查`TensorEqual`：288次，累计3.523秒。这是保证作者codec位差时退回原字节的必要检查，当前实现把该开销算入了训练。
- 编码`compBF16`及`merge`累计约0.050秒；编码内核本身不是最大开销。更新内的宿主`weight/encode_verify`范围5.305秒，包含等待、复制及校验，不能再与内核累计相加。
- 原MatMul仍11520次，累计约16.29秒，原版约16.37秒；TransData仍5760次，约0.636秒。没有证据表明原模型矩阵计算或格式转换突然变慢。

更新尾部采样范围新增约3.66秒设备计算，原版该范围几乎没有设备计算，与更新后编解码/逐位检查相符。复制互斥覆盖增加6.62秒也已测到，但尚未逐方向、逐来源完全归因；不把它全部说成CPU到NPU传输，也不凭此认定某种布局问题。

因此，本实现的明确问题是：重复重建权重和每轮更新验证给设备增加额外工作，CPU累积减负不足以覆盖。这个结果否定的是这版实现的净收益，不证明所有在线无损压缩必然更慢。

## 数值检查与预热

最终生产代码另跑tiny连续三步，全部梯度、CPU FP32 master及Adam m/v与原流水线逐位相同，独立首步参考也通过。27B所有初始压缩矩阵按int16位型相同；每rank每轮288个更新帧编码后逐位检查，位差或膨胀保存原字节。

27B四轮梯度范数与原版完全一致，数据/顺序/长度/padding/851参数形状/48层重算/FP32状态审计通过。相同768条后的短验证仍loss **0.855101466178894**、205/224，与原版一致。这是已测短窗口的结果，不代替长期收敛测试。

第一轮预热385.89秒，其中更新回传约307.37秒，明显异常于后续正常轮。其具体初始化长尾来源尚未隔离；编码校验宿主累计约6.45秒，不把307秒全部归咎于codec。完整保留首轮记录，按原口径排除预热，不隐藏该成本。

原4GiB版三项源码哈希、原ZeRO入口八项哈希均未变。试验进程正常退出，物理2/3卡释放，其他任务未动。
