# 固定每256条更新一次：当前训练瓶颈

本轮只定位瓶颈，不把更改更新次数算作系统加速。固定两张910B2、global batch256、每卡micro16、累积8、原768条训练数据、max512动态padding、全64层重算。BF16计算与CPU FP32主权重/Adam m/v保持原配置。

结论：反向阶段的梯度处理、卡间通信和CPU↔NPU往返是优先处理的系统开销；CPUAdam不是唯一或最大的开销。不能将反向总时间全称为矩阵乘计算，也不能把所有等待归因于显存带宽。

## 同一工作量的时间

原无采样稳态为107.97秒/256条。本轮前两步143.63秒（冷启动）、105.55秒；最后一步rank0完整采样114.12秒，rank1等待结束114.26秒。采样不替代原测速。

最后一步rank0设备窗口114.1468秒，按统一时间轴取区间并集并排除重叠：

| 互不重叠的区间分类 | 秒 | 解读 |
|---|---:|---|
| 有计算任务，包括与通信/复制重叠 | 51.80 | 算子实际覆盖的时间；不代表每个计算单元都满载 |
| 无计算、有卡间通信任务 | 26.20 | AllGather/ReduceScatter等任务，包含通信中的等待；不等于纯链路传输时间 |
| 无计算/卡间通信、有MEMCPY_ASYNC | 14.93 | CPU↔NPU等异步复制任务的覆盖区间；本表不能单独把它全归到梯度 |
| 以上三者都无、CPUAdam计算中 | 9.73 | 44次原生CPUAdam调用 |
| 其他区间 | 11.49 | 主机调度、缩放、格式转换提交、依赖等待及未纳入上述分类的工作 |

总计114.15秒。不能把通信累计51.28秒、计算累计55.07秒、复制累计28.02秒直接相加：它们存在重叠。卡间通信与计算重叠约25.07秒，未与计算重叠约26.20秒。即便某段没有计算任务，也不等于可以无代价消除全部耗时。

## 梯度为何往返

检查安装中的DeepSpeed Stage3实际源码，并在原方法外增加进程内观测：

1. 每个小批次反向后，FP32通信做ReduceScatter，获得本rank梯度分片；原配置的累积缓冲使用BF16，不在本轮改变。
2. 累积缓冲在CPU；下一批梯度到来时，旧分片回到NPU相加，再写回CPU。首批也存在先写CPU再回NPU的原生路径。
3. 最终边界还将梯度写入CPU FP32优化器梯度缓冲。

每rank每次256条更新，实际观测到H2D6808次、215,167,987,712字节；D2H8181次、268,959,984,640字节；合计484,127,972,352字节，约484.13GB。两rank合计约968.26GB。此处只统计梯度分片/卸载路径，不包含全部参数AllGather，也不包含更新后每rank约26.90GB计算权重回传。

这些是实际张量复制提交的逻辑字节，不是硬件链路计数。梯度复制的主机API区间合计约2.05秒，因为异步提交很快；不能因此认为传输只花2秒。反之，也不能将设备复制28.02秒全部认定为梯度阻塞时间。

## 算子与通信证据

- 计算任务225071次，累计55.07秒，去重覆盖51.80秒；MatMulV3累计24.63秒，GDN prepare_wy_repr_bwd约5.06秒，其余包含Mul/Cast/Transpose等。
- AllGather4721次，累计26.03秒；ReduceScatter4504次，累计25.24秒；AllReduce约0.001秒。通信任务时间包含执行及依赖等待，不能直接解释为物理互联带宽不够。
- zero/reduce_and_partition主机范围33.32秒，其中partition8.46秒、average_scatter6.42秒；这些为嵌套范围，不能相加。Event::synchronize主机累计18.15秒，同样可能嵌套于前述范围，不能再加一次。
- CPUAdam9.73秒，梯度缩放约2.05秒、CPU BF16转换约1.63秒。单纯消除CPUAdam计算也最多覆盖本窗口约8.5%，不是数倍加速来源。

下一步应针对梯度累积的CPU/NPU往返和4504次梯度归约的调度研究，保持每256条更新一次与同一数据工作量；优先减少数据交换的暴露时间，再谈矩阵乘微优化。是否采用驻留窗口、调整合并或CPU累积，需要容量、时序和数值验证，本轮没有实施，也没有承诺收益。

## 可靠性与复现

`probe_observer.py`先核对复制计数及张量值；`gradient_scopes.py`保留原方法、操作和返回值，只观察。完整三步正常退出；最终验证loss0.8581519723、204/224，与上一轮g256一致。8条验证仅检查本轮观测未改变短跑结果，不能证明长期质量。

`analyze_gradient.py`复用数据库技能的compute/comm宏，先校验正常Stop元数据与Db导出，再只读查询。没有配置msprof MCP，使用只读SQLite执行同样SQL。`PYTORCH_API`时间戳在此版本为TEXT，跨表时显式转INTEGER，避免排序把两种类型分开；时间轴分类总和必须等于设备窗口。

过滤结果见仓库`evidence/2026-10-25/sql-bottleneck-profile.json`（含完整SQL）和`sql-bottleneck-observation.json`。原始数据库留在服务器独立实验目录，不提交权重、数据正文或原始采样。2/3卡已无训练进程；原模型和其他服务未改动。
