## 已有收益及适用范围

- k1 C/OpenMP BF16加法内核保留逐micro加法和BF16舍入；历史CPU复放46.24→39.77秒。完整默认配置的rank0 CPU累加45.63→29.53秒。

## 对照同时改变了缓冲

`cpu_fused.py`为所有参数预留整份pinned stash，k1不是仅替换`.add_`：按rank0的13,447,996,672元素，stash25.05GiB；k2两份约50.10GiB。原接收区为16×128MiB=2GiB。原报告约54的量指十进制GB，不能直接写54GiB。

CPU加法和缓冲/复制/线程调度一起变化，整步未提速本身不能单独证明原CPU加法绝不在关键路径。worker等event上升也包含依赖，不是纯DMA传输时间。原报告的93.27/94.29观测保留，但对应强因果解释需要收窄。

## 已复现的缓冲覆盖

生产端hook仅在`_stage_count[idx][parity] != 0`时阻止复用；但是这个计数在worker等event返回之后才增加，生产端提交搬运时没有先把该区标记占用。若worker尚未确认上一份数据，计数仍为0，下一micro可覆盖相同stash区。k1只有一份stash，因而同一参数相邻micro直接复用同一区域。

`probe_buffer_reuse.py`通过原模块支持的event_factory和lib注入完成以下CPU检查，原FusedOffload未修改：

1. 提交梯度1，延迟consumer的event确认；此时stage_count仍0。
2. 下一micro提交梯度2，复用同一区域。
3. 允许worker继续，两次均读到2，得到4；正确顺序结果应为3。

8个BF16元素全部复现。顺序控制组在每轮排空后再提交，8个元素都得到3。使用CPU参考加法避免把C数值问题和队列生命周期问题混在一起；无pinned分配、无NPU事件、无需编译C核，未改真实训练进程。此探针证明存在可发生的错误时序，不证明历史27B运行已经触发错误。
