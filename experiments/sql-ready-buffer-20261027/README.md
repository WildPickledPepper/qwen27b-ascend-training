# 就绪数据供应与流水缓冲：独立验证进行中

2026-10-27用户要求接收、待处理、CPU累加解耦，优先让CPU持续处理。原实现16×128MiB锁页槽本来就有接收缓冲作用，CPU累计梯度也单独存储；不能把原槽称为完全无缓冲作用的“工作区”。原FIFO任务可能尚未完成D2H，CPUworker在完成事件上等待；D2H与NPU计算同流，主线程拿不到槽则阻塞。

新副本不增加CPU槽→工作区的额外memcpy，而是独立的有界显存待搬队列、私有D2H流、完成监视线程、ready-only CPU FIFO。32×128MiB CPU接收槽共4GiB，CPU直接消费已完成槽并加到原accum；容量不足的背压转移到512MiB额外非驻留梯度待搬预算，不是无限积压。原4/8GiB驻留不计额外待搬预算，保持16micro同参数相加顺序。生产/复制event与record_stream/显式引用共同保护生命周期。

只在实时空闲3/4卡，global256/micro16/原SQL768条、48层重算、BF16、CPU FP32 master/m/v、512token连续化loss、24核NUMA规则不改。先tiny三步对原tiny全部grad/master/m/v逐位比对，通过后才27B三步；tiny已通过。复用刚完成的4/8对照，不重复基线。主入口、共享库及模型文件不改。

新计时分别报告主线程等显存预算、复制线程等CPU槽、完成监视等event、CPU相加、相邻add之间的空隙，保存host Chrome trace。事件监视等待包含依赖，不是纯DMA耗时；CPU busy率以第一至最后一次相加区间计算，排除初始填充，不能靠延迟启动CPU造高利用率。整步耗时仍为最终指标，不承诺持续100%或先宣称收益。

当前仅tiny逐位通过，完整27B进行中。完成将记录实际显存、精度、CPU供应空隙、整步时间并清理自身任务。历史独立复制流未提速的结果仍保留；本轮组合策略不宣称已逐项分离因果。
