# 接收缓冲与独立D2H流水：验证完成，未采用

2026-10-27用户要求缓冲解耦、优先让CPU持续工作，随后明确先核对单块容量和原双缓冲。原每次CPU add处理一个有效片段，最大64M BF16元素=128MiB；16槽共2GiB，已经超过两块256MiB的双缓冲最低容量。原槽本来就是多缓冲接收区，accum另存；之前“原来没有流水缓冲”的解释撤回。原CPU累加与后续NPU任务已可重叠；缺少充分解耦的是默认计算流上的D2H调度，以及未就绪FIFO/主线程等槽的耦合。

## 实现及固定条件

在独立副本加入512MiB非驻留梯度待搬队列、私有D2H流、完成监视线程、ready-only CPU FIFO，并将锁页槽16扩到32×128MiB（4GiB）。这是一组组合改动，不能据此分离容量或复制流的单独贡献。CPU直接累加已完成接收槽，无额外槽→工作区memcpy。保持同参数BF16相加顺序、源tensor所有权与record_stream/event依赖；4/8GiB原驻留累加不算额外待搬预算。

物理3/4实时空闲，Qwen3.5-27B文本全参、自定义PyTorch/Transformers两段1F1B、global256/micro16/16micro、原SQL768条及padding、48层非重入重算、BF16计算/梯度、CPU FP32主权重/m/v、512token连续化loss和24核NUMA规则不变。原入口/共享库/模型不改。tiny三步全部grad/master/m/v逐位通过才27B三步；第一步lr0预热、后两步计时，复用刚完成4/8对照。

## CPU有没有持续工作

| 第一至最后一次相加跨度 |59.90秒|59.36秒|
| 累加忙时比例 |89.16%|67.78%|
| 每步最长相邻add空隙均值 |0.484秒|1.503秒|

空隙包括缺数据、调度与Python开销，不全是纯搬运等待。旧版本没有相同逐add事件，不能用旧event等待9.35/14.45秒与新空隙作直接收益对比。

完成事件结束与CPU add开始时间可重建就绪数的近似上界：两卡观察到过31块；3号约99.59%的取块点已有至少两块就绪，4号约93.2%–93.7%。这按取块次数统计，不是按时间：少数长时间断粮仍可累计很多秒。完成事件时间略早于实际入ready FIFO，派生深度是近似，未冒充精确队列快照。
