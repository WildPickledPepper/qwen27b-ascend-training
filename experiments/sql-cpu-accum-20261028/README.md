# CPU 梯度累加加速：融合 BF16 内核（已采用候选）+ 两 micro 合批（已否决）

**结论**

1. 当前 CPU 累加不是“并行不足”：torch 本来就是多线程，24 核已经吃满这条 NUMA 节点的带宽。
2. **手写 C 内核（`k1`，加法顺序不变）在固定 256 条、同窗口 A/B 下把步时从 133.82 秒降到 121.09 秒（−9.5%）**，CPU 累加从 49.5 秒降到 33.1 秒（−33%），主线程等槽从 36 秒归零；**三步后验证 loss 与梯度范数与 torch 完全一致**（0.855101469、40.502924/40.572267/38.679349），tiny 三步 23/23 参数逐位一致。
3. 两 micro 合批（`k2`）在 CPU 复放里最快（46.24 → 31.40 秒），但**端到端反而慢于 k1**（128.65 秒）：54 GiB pinned 中转区的首次触页、大块 pinned 的 D2H 变慢、范数段退化把收益吃光，且数值不再逐位等价（loss 0.858709335）。**否决**，理由与证据保留。
4. **撤回**上一轮“每步 8 个 micro、D2H 有 1.7 倍重复搬运”的判断：实际每步 **16 个 micro**（`selected_parameters=29`，`resident_add_calls=464=29×16`），366 GB D2H 正好等于 16 遍减掉驻留部分。没有重复搬运。

**状态：`k1` 是采用候选，但 81.22 秒入口暂不改默认**，先做更长训练确认收敛；`--cpu-accum` 默认仍是 `torch`。

## 账本（来自 `cache4-full` 的 rank0/1，非估算）

| 指标 | 每步每卡 | 说明 |
|---|---|---|
| 步总时长 | 80.20 / 82.23 秒 | 前向 4.4 + 反向 52.9 + 尾部约 22.9 |
| CPU 累加 | 47.19 / 48.91 秒 | 占反向窗口 89% |
| D2H | 365.91 GB | 16 遍 × 每卡 13.45e9 元素，减 4 GiB 驻留 |
| 主线程等空槽 | 32.5 秒 | 消费端（CPU 加法）跟不上生产端 |
| 累加器流量 | 1.10 TB | 16 遍 × 6 B/元素（读梯度 2 + 读累加 2 + 写累加 2） |
| 有效带宽 | 23.3 GB/s | 干净环境同机上限 26–32 GB/s |

## 做过的无效方向（保留，避免重复踩）

| 尝试 | 结果 |
|---|---|
| 线程 24 → 16 / 20 / 32 | −5% ~ +3%，在噪声内 |
| `madvise(MADV_HUGEPAGE)` 大页 | 反而更慢（一次读数 27.09 ms vs 15.90 ms，噪声大） |
| 双 NUMA interleave（节点 4/5，48 线程） | 仅 +9% |
| Python 层 2 MiB 分块合批 | 更慢（12.8 GB/s），逐 op 线程调度开销吃掉收益 |
| k=4（4 条读流） | 41.25 秒，比 k=2 慢：预取被 4 条流打散 |
| 合成干扰测试（后台 memcpy 4.6–13.8 GB/s） | 未见稳定减速，说明“D2H 把 CPU 加法拖慢一倍”的旧结论依赖很强的干扰条件 |

## 实现

| 文件 | 作用 |
|---|---|
| `cpu_fused_accum.c` | `accum1`（与 torch 等价的 bf16 加法，f2bf 用 RNE）与 `accumk`（k 份梯度先在寄存器里求和再写累加器） |
| `cpu_fused.py` | 乒乓 pinned stash、逐参数“成对完成即 fuse”、NPU 事件同步、奇偶槽复用门（写同一槽前必须等上一次 fuse 结束） |
| `build_entry.py` | 由 81.22 秒入口生成 `train_accum.py`：只替换累加实现、插入 micro 边界、把设备断言改为 0/3 |
| `run_sequence.py` | 只用物理 0/3 的串行控制器（每次启动前 `npu-smi` 确认空闲） |
| `bench_cpu_accum.py` | CPU-only 复放：按 manifest 的真实切片序列跑 torch/k1/k2，交错取中位数 |

`k2` 的数据路径：每 micro 的梯度 D2H 直写 `stash[micro%2]`（不再经过 16×128 MiB 小槽），同一参数两个奇偶都到齐后在 worker 线程 fuse 一次，随后两个槽可复用。因此需要 `2 × 参数总量` 的 pinned 主机内存（本模型每 rank 约 54 GB）；实测 54 GiB `pin_memory` 14.5 秒成功，`ulimit -l` 允许 270 GB。

## 验证

tiny 三步（同一参考梯度，`tiny_gradient_comparison`）：

| 模式 | 逐位一致参数 | 最大偏差（占参数尺度） |
|---|---|---|
| torch（原路径） | 23/23 | 0 |
| k1（内核，同顺序） | 23/23 | 0 |
| k2（两 micro 合批） | 0/23 | 1.2%（≈3.1 bf16 ulp） |

k2 的偏差来自 bf16 加法重排，属于该口径固有的噪声量级；**不声明与顺序累加逐位等价**。

## 端到端（固定 256 条、物理 0/3、同窗口 A/B）

同窗口一对：torch 与 k1 连续跑，起步 load 均为 126.94（期间 50–177 波动，只看相对值）。

| 模式 | 步 2/3 均值 | CPU 累加（r0/r1） | 主线程等槽 | 验证 loss（768 条后） | 判定 |
|---|---|---|---|---|---|
| torch（对照） | 133.82 秒 | 49.96 / 49.02 秒 | 36.2 秒 | 0.855101469，205/224 | 基准 |
| **k1 内核** | **121.09 秒（−9.5%）** | **31.01 / 35.16 秒（−33%）** | **0.0 秒** | **0.855101469，205/224（逐位同）** | 采用候选 |
| k2 合批 | 128.65 秒 | 33.6 / 39.4 秒 | 0.0 秒 | 0.858709335，205/224 | 否决 |

补充对照（不同负载窗口，仅作参照）：torch 在 load 177 时 154.5 秒、在 load 105 时 117.6 秒。

要读出的三件事：

1. **约束从 CPU 加法转到了 D2H**：k1 的等槽归零、worker 等事件从 11 秒升到 31 秒——累加器不再是下游瓶颈，继续优化要转向搬运本身。
2. **k2 的账**：CPU 复放里最快，端到端却慢于 k1，因为 copy_wait 41 秒（k1 31 秒）、范数段 31 秒（k1 16 秒）、首步尾部 483.8 秒（54 GiB pinned 首次触页）。教训：**局部流量最优 ≠ 端到端最优**。
3. **数值**：k1 的三步梯度范数与 torch 完全相同（40.502924 / 40.572267 / 38.679349），k2 不同（40.504828 / 40.571747 / 38.648928）。

## 局限

- 机器是共享的（对照期间 load 50–177），单次读数噪声很大，所有比值优先看同窗口交错或相邻运行；本轮的同窗口对起步 load 相同，但运行期间仍有波动。
- 只做了 3 步 + 8 条短验证，没有长期收敛结论；k1 虽逐位一致，仍需更长训练确认。
- 默认入口（81.22 秒）未改，`--cpu-accum` 仍默认 `torch`；k1 是显式开关。
