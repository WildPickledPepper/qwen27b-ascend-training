# CPU 梯度累加：融合 BF16 内核（在默认配置下无收益）与两 micro 合批（否决）

**结论（含对前一轮的更正）**

1. **用仓库默认配置复现（`sql-pipeline-overlap-20261026` 的 `run_selected.py`，只把写死的 `2,3` 改成 `0,3`，源文件哈希与 `selected-profile.json` 一致）：93.27 秒/256 条；再把累加换成融合内核 `k1` 是 94.29 秒（+1.1%，噪声内）。** CPU 累加从 45.6 秒降到 29.5 秒、主线程等槽从 34 秒归零，但**步时不变**。
2. 因此：**在这套配置里 CPU 加法不是关键路径**，它已经被反向计算（约 55 秒）盖住；把 16 秒的累加时间拿掉，只是让主线程更早把 D2H 排进队列（worker 等事件从 11 秒升到 30 秒以上），换不出步时收益。
3. **更正前一轮的 −9.5%**：那是 `--norm-device cpu` 变体上的结果（范数段在 CPU 上要 46 秒，k1 才有用）。同变体低负载复测：133.19 → 123.78 秒（−7.1%）。该变体**不是**仓库默认配置，不能代表 81.22 秒口径。
4. 两 micro 合批 `k2` 端到端更慢（128.65 秒，同窗口 k1 121.09）：54 GiB pinned 中转区的首次触页、大块 pinned 的 D2H 变慢与范数段退化吃掉收益，且数值不再逐位等价（0.858709335）。**否决**。
5. **撤回**更早“每步 8 个 micro、D2H 有 1.7 倍重复搬运”的判断：实际每步 **16 个 micro**（`selected_parameters=29`，`resident_add_calls=464=29×16`），366 GB 正好等于 16 遍减掉驻留。没有重复搬运。

**状态：不采用。默认入口（81.22 秒口径）保持原样；`--cpu-accum` 保留为可选开关，结论是“在这套配置下无收益”。**

## 做过的方向与结果

| 尝试 | 结果 |
|---|---|
| 线程 24 → 16 / 20 / 32 | −5% ~ +3%，噪声内 |
| `madvise(MADV_HUGEPAGE)` | 反而更慢（27.09 vs 15.90 ms，噪声大） |
| 双 NUMA interleave（节点 4/5，48 线程） | 仅 +9% |
| Python 层 2 MiB 分块合批 | 更慢（12.8 GB/s），逐 op 线程调度开销 |
| k=4（4 条读流） | 41.25 秒，比 k=2 慢：预取被打散 |
| **k=1 融合内核** | CPU 复放 46.24 → 39.77 秒（1.16×，逐位一致）；**默认配置端到端无收益** |
| **k=2 两 micro 合批** | CPU 复放 31.40 秒；端到端更慢，且非逐位等价 |

## 实现

| 文件 | 作用 |
|---|---|
| `cpu_fused_accum.c` | `accum1`（与 torch 等价的 bf16 加法，RNE）与 `accumk`（k 份先在寄存器求和再写累加器） |
| `cpu_fused.py` | pinned stash、逐参数成对 fuse、NPU 事件同步；`k1` 也走大 pinned stash（不再用 16×128 MiB 小槽），这是 worker 等事件升高的原因 |
| `build_entry.py` | 由默认入口生成 `train_accum.py`：只替换累加实现、插入 micro 边界、设备断言改 0/3 |
| `run_sequence.py` | 只用物理 0/3 的串行控制器；`replay81` 计划复现默认脚本 |
| `bench_cpu_accum.py` | CPU-only 复放：真实切片序列上跑 torch/k1/k2，交错取中位数 |

## 局限与下一步

- 机器负载在 27–177 之间波动；81.22 秒是历史低负载值，**本轮同脚本复现是 93.27 秒**，说明当前机器状态整体更慢，绝对秒数不能与历史值直接比。
- k1 让 worker 等事件从 11 秒升到 30 秒以上：约束从“CPU 加法”转到“搬运”。要继续提速，应该打 D2H/流水，而不是继续磨累加器。
- 只做 3 步 + 8 条短验证，没有长期收敛结论。
