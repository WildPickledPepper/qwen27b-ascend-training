# 缓冲流水变慢：CPU原生累加与实际D2H的隔离分析

2026-10-28。用户认为CPU空等已解决，要求解释77.83→79.59秒。先核实前提：ready-only worker只是不再在累加线程里等待D2H event，并不保证有就绪数据；新3号相邻add之间仍有6.49秒、4号19.12秒空隙。只读原host trace进一步拆得，3号内部ready.get等待6.16秒、其余add间开销约0.34秒；4号ready.get约18.85秒，其余约0.27秒。初始填充不含在这些区间。

## 定向隔离：同一批内存，仅切换真实搬运

没有重跑27B训练。先检查物理3空闲，固定CPU96–119、NUMA preferred4、24个Torch CPU线程；同一进程保留同一批25.05GiB CPU目标数组、32×128MiB锁页输入槽、128MiB NPU常量源。每次处理128个完整块共16GiB；输入均为1、目标每次清零。校验每块抽样结果正确。没有模型权重、前后向、Adam或数据集更新。

先做探索：16/32槽、CPU-only/真实D2H/记录开关，两轮正反顺序。首次cpu16有明显冷启动，因此不把那一点平均作容量因果；子线程CPU profiler产生初始化回调警告但完整返回128个add。探索原始结果保留。正式事件对照另进程，先预热、CPU consumer与CPU profiler都在主线程，正反顺序各一次；同一分配地址贯穿四种模式。

真实并发D2H下，CPU add外层慢52.70%。原生add也同步增加，外层计时减原生仅约0.006秒，不支持将此实验增量主要归咎Python收尾/GIL或日志。仅队列和event比CPU-only约多0.026秒，打开轻量记录没有稳定明显增量。实际内存复制发生时才有显著增量，验证了D2H工作与CPU加法并行时存在性能干扰。

机制上，D2H要写CPU接收内存，CPU累加要读接收槽并读写累计梯度；它们不是完全独立的资源使用者。此实验定位到“真实搬运并发使原生CPU add变慢”这一级，不进一步声称DDR控制器、NUMA链路、缓存一致性或驱动调度各占多少：未采这些硬件计数。不要把52.70%直接套到整模型；模型里并发强度、块大小、页落点和外部负载均不同，也不能宣称历史多出的5.52秒已全部逐秒解释。

## 对后续优化的含义

CPU忙时变高不等于每秒处理更多梯度；只减少等待却拖慢每次add，会吃掉流水收益。下一步应针对搬运与CPU加法同时执行时的资源效率做受控分析，保持单因素和原训练数学；不是继续盲目扩大缓冲或把并发当必然加速。本轮只完成分析与小型受控验证，不自动启动新训练或进一步优化。
