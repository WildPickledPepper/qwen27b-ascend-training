# 缓冲流水变慢：CPU原生累加与实际D2H的隔离分析

2026-10-28。用户认为CPU空等已解决，要求解释77.83→79.59秒。先核实前提：ready-only worker只是不再在累加线程里等待D2H event，并不保证有就绪数据；新3号相邻add之间仍有6.49秒、4号19.12秒空隙。只读原host trace进一步拆得，3号内部ready.get等待6.16秒、其余add间开销约0.34秒；4号ready.get约18.85秒，其余约0.27秒。初始填充不含在这些区间。

## 整模型变慢的位置（原实验，只读复核）

两组同为global256/micro16/原SQL768条/48重算/BF16/CPU FP32 master-m-v/4-8GiB驻留/512token loss。原16槽同流与新32槽独立D2H等组合策略并非单因素比较。

|---|---:|---:|---:|
| 前后向及排空 |63.2491秒|64.7663秒|+1.5172秒|
| 全局范数阶段 |1.3636秒|1.3767秒|+0.0132秒|
| 更新/回传/末尾同步 |13.2170秒|13.4462秒|+0.2292秒|
| 整步约 |77.8298秒|79.5893秒|+1.7594秒|

CPU累加本身3号47.8831→53.4040秒，多5.5209秒；4号38.2781→40.2343秒，多1.9562秒。D2H总字节、驻留调用、输入/padding、范数和短验证相同。CPU累加与设备工作重叠，不能把多5.52秒直接加进整步。

## 定向隔离：同一批内存，仅切换真实搬运

没有重跑27B训练。先检查物理3空闲，固定CPU96–119、NUMA preferred4、24个Torch CPU线程；同一进程保留同一批25.05GiB CPU目标数组、32×128MiB锁页输入槽、128MiB NPU常量源。每次处理128个完整块共16GiB；输入均为1、目标每次清零。校验每块抽样结果正确。没有模型权重、前后向、Adam或数据集更新。

先做探索：16/32槽、CPU-only/真实D2H/记录开关，两轮正反顺序。首次cpu16有明显冷启动，因此不把那一点平均作容量因果；子线程CPU profiler产生初始化回调警告但完整返回128个add。探索原始结果保留。正式事件对照另进程，先预热、CPU consumer与CPU profiler都在主线程，正反顺序各一次；同一分配地址贯穿四种模式。

| 正式对照，16GiB累加，两轮均值 |外层add墙钟|原生aten::add_墙钟|等就绪数据|
|---|---:|---:|---:|
| CPU-only，32槽 |1.43919秒|1.43328秒|0.00029秒|
| 保留复制/完成线程、FIFO、NPU events，但不做memcpy |1.46521秒|1.45887秒|0.00103秒|
| 真实并发D2H，32槽 |2.19764秒|2.19190秒|0.00829秒|
| 真实D2H＋轻量host记录 |2.19575秒|2.18993秒|0.00767秒|

真实并发D2H下，CPU add外层慢52.70%。原生add也同步增加，外层计时减原生仅约0.006秒，不支持将此实验增量主要归咎Python收尾/GIL或日志。仅队列和event比CPU-only约多0.026秒，打开轻量记录没有稳定明显增量。实际内存复制发生时才有显著增量，验证了D2H工作与CPU加法并行时存在性能干扰。

机制上，D2H要写CPU接收内存，CPU累加要读接收槽并读写累计梯度；它们不是完全独立的资源使用者。此实验定位到“真实搬运并发使原生CPU add变慢”这一级，不进一步声称DDR控制器、NUMA链路、缓存一致性或驱动调度各占多少：未采这些硬件计数。不要把52.70%直接套到整模型；模型里并发强度、块大小、页落点和外部负载均不同，也不能宣称历史多出的5.52秒已全部逐秒解释。

## 对后续优化的含义

CPU忙时变高不等于每秒处理更多梯度；只减少等待却拖慢每次add，会吃掉流水收益。下一步应针对搬运与CPU加法同时执行时的资源效率做受控分析，保持单因素和原训练数学；不是继续盲目扩大缓冲或把并发当必然加速。本轮只完成分析与小型受控验证，不自动启动新训练或进一步优化。

## 后续：为什么有缓冲仍空等，以及为什么32槽

32槽是上轮从16翻倍的试验参数，每槽128MiB不变，CPU锁页接收池从2GiB变4GiB；没有依据生产/消费速率推导最优容量。原16槽已经满足多缓冲，不能以“实现双缓冲”为扩容理由。同一次改流/队列和容量混入因素，未得到净收益，不采用32槽组合；后来的小型事件隔离实验全部固定32槽是为去掉容量变量，不是在证明32优于16。

本轮只读已有host trace，逐块按FIFO配对CPU get、D2H下发、完成通知和CPU add。第一至最后一次add内的ready.get等待拆分（两步均值）：

| 阶段 |3号|4号|
|---|---:|---:|
| 所需下一块的D2H调用尚未开始 |2.5548秒|8.7065秒|
| D2H下发调用本身 |0.0019秒|0.0093秒|
| 已下发，等完成通知 |3.5556秒|10.0736秒|
| 收到完成通知后至CPU取到 |0.0445秒|0.0581秒|
| ready.get合计（不含初始填充） |6.1568秒|18.8475秒|

后半段包括计算依赖、复制队列/传输及监视调度，不能当纯PCIe耗时。与相邻add总间隙6.49/19.12秒的差额是其他主机开销。

例1：4号第2步，7.987647秒开始等下一块，8.605992秒才开始该块D2H下发，8.606169秒下发返回，9.127416秒完成监视返回，9.127460秒CPU get返回。该1.139812秒等待约0.618秒在下发前、约0.521秒在下发后。中点约8.5576秒，按槽获取、完成与add时间重建：32槽全空闲、0块就绪。不能用“槽满，无接收空间”解释这一段；是没有已到位数据可取。主线程待搬预算记录在7.9505至8.6056秒间没有新的交付记录，但不能据此断言NPU没有产生任何梯度，部分梯度可能仅在驻留缓存累加。

例2：3号第2步，11.242159至约11.7353秒等待，期间中点约7个槽被已下发但未确认完成的任务占用、约25个空槽、0块就绪。这里有接收空间，但尚无完成的数据。状态由host事件重建，队列操作有微小时间差，不是直接槽状态快照。

结论：缓冲提供的是容量，不自动保证一直有就绪数据；要跨过供数空隙必须提前积累足够已完成的数据。看到空等时槽未满并不能推断任何更大容量都无收益，也不能证明继续扩容会更快。现在已定位到“下发前的供数空隙”和“下发后的完成等待”两段；具体等待哪个NPU计算任务需设备trace，不能再靠这份host记录命名算子根因。
