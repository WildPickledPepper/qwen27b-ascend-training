# 完整FP32 baseline的CPU offload优化

后3步平均由 **161.76秒降至76.35秒**，约 **2.12倍加速**，同一次更新耗时减少约52.8%。没有引入量化：权重、计算、梯度及CPU m/v继续FP32，保留原NPU Adam更新公式。2/3卡已释放。

## 结果

| 阶段，后3步平均 | 原完整FP32 baseline | 优化后 |
|---|---:|---:|
| CPU→NPU状态拷入 | 60.78秒 | 34.67秒 |
| NPU→CPU状态拷回 | 52.53秒 | 20.11秒 |
| 双向搬运阶段合计 | 113.31秒 | 54.77秒 |
| 显式Adam更新段 | 12.92秒 | 2.01秒 |
| 整步 | **161.76秒** | **76.35秒** |

| 训练步 | 原baseline整步 | 优化后整步 |
|---|---:|---:|
| 1 | 492.22秒 | 387.65秒 |
| 2 | 190.72秒 | 114.85秒 |
| 3 | 154.56秒 | 60.82秒 |
| 4 | 139.99秒 | 53.37秒 |

首步回传受冷启动显著影响：原359.82秒、新321.65秒。因此保留所有步数，后3步均值不是已经充分稳定的长跑吞吐，更不把微测试53%直接当成整模型结果。原已完成baseline复用，不重新跑基线。共享服务器有其他任务，未宣称这是整模型严格同时的双因素实验。

## 改了什么，为什么

原方法将每份m/v按1,048,576个FP32数分块，即每份4 MiB。每块临时生成NPU状态张量、拷入、同步、执行多次点操作、同步、拷回；851个参数张量跨全模型重复这个过程。

新配置扩大为16,777,216个FP32数，即每份64 MiB。与现有归档的最大原始权重帧大小一致，常见64 MiB帧不再切成16个小窗口更新。每次处理更多参数，减少重复分配、拷贝下发、有限值检查、同步与Adam操作下发次数；总状态字节数和数学公式不变。这里是优化器参数窗口，不是训练batch或NF4的B128。

同时将本进程4个CPU线程的亲和设到96–99，对应连接物理2/3卡的NUMA4。没有修改全局NUMA或THP设置。**CPU绑核不等于全部状态内存就近**：加载321张量时一次匿名内存采样约54.89 GiB在节点4、138.25 GiB在节点5；两节点系统距离11，本地为10。没有把绑核效果单独量化或宣称严格本地分配。完整模型应用了两项改动，不能把全部收益只归因于其中一项。

## 先做了什么对照

同进程、相同CPU亲和、相同33,558,528坐标、每组3次更新、含非整窗口尾部，在两张卡核对原始CPU FP32 m/v驻留、NPU FP32更新。以下为各组后两步平均秒数：

| 方法 | 物理2卡 | 物理3卡 |
|---|---:|---:|
| 原方法4 MiB窗口 | 0.13187 | 0.12955 |
| 原方法64 MiB窗口 | 0.06105 | 0.06299 |
| 锁页双slot流水4 MiB | 0.10857 | 0.10536 |
| 锁页双slot流水64 MiB | 0.05914 | 0.06024 |

四种方法的完整测试权重、m、v与参考逐位一致。窗口是该小测主要收益来源；64 MiB下流水的额外改善仅约3–4%。因此先将原始大窗口方法接入整模型，锁页流水原型只留作后续候选，没有自动混入本次整模型结果。第一次16,781,312坐标对照也通过，见setup证据。

## 精度和内存

与原baseline一致：相同初始归档、4条完整训练样本28/31/31/32 token、batch1、相同学习率/Adam超参数、相同8条独立验证/433个assistant token，GSM8K不进入训练。训练全部26,895,998,464文本参数；每步完整覆盖，Parameter.grad用完清空。

- 4步每步52,928个确定性抽样坐标，覆盖851个张量：梯度、更新量、更新后权重的最大差均0。只代表这些坐标，不冒充整模型所有位或全部m/v核对。
- 原统一FP32验证loss **1.53496370194**，新 **1.53496371158**，差约9.64e-09。
- assistant逐token正确率均 **60.7390%**；不是整题正确率，8条短验证不代表长期质量认证。
- 每卡NPU分配峰值：原50.93/50.83 GiB，新51.18/51.08 GiB，约多0.25 GiB/卡。
- 进程CPU RSS峰值约202.81 GiB，完整FP32 m/v约200.39 GiB；不保留整模型BF16副本，没有FP32状态低比特压缩。
- 原模型只读，没有保存/覆盖原模型；自己的任务退出，2/3卡均无进程，其他任务不动。没有自动Git提交/推送。

## 下一步优先级

当前双向搬运阶段仍约54.77秒，占整步约71.7%；显式Adam段只约2.01秒。下一轮应围绕状态搬运与其等待做进一步流水/缓冲核对，而不是重新引入此前297秒的4-bit更新路径。小测流水额外收益小，尚未证明在200 GiB全模型工作集上的收益，不能直接当作已实现加速。

实际训练吞吐还应考虑每次更新的有效token数。当前仅28–32 token却更新全部27B状态，固定开销摊得很重；更大microbatch或完整样本打包可以作为下一轮单独协议。梯度累积不能直接接到当前“每次反向立即更新释放”的实现上，需先保持每次优化器更新的正确语义，并计入梯度缓冲/卸载成本。改变batch后的tokens/s和训练质量不与本轮同batch加速混称。
