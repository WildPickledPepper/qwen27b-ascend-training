# BF16计算权重与FP32主权重训练验证

日期：2026-10-24，Asia/Shanghai。用户明确授权采用BF16计算、FP32主权重，并增加训练步数。本轮目标为20步全参数短训练，物理2/3号910B2，复用原始模型与独立训练/验证划分。当前结果以文末状态为准。

## 精度与存储

- 线性层NPU常驻BF16计算权重，CPU持有未经BF16舍入的FP32主权重和完整FP32 Adam m/v。
- 大矩阵前向、反向使用BF16；线性层输出回FP32。GDN、注意力、归一化、嵌入与微小原生参数沿用FP32，不使用全局autocast。
- CPUAdam沿用之前验证的DeepSpeed NEON数学实现及有界传输流水。没有量化Adam状态；没有改共享安装或原模型。
- 训练是既有分片自定义harness，不是NeMo/DeepSpeed训练引擎的吞吐上限。

## 实际执行与失败保留

1. 双卡各3步优化器小测：CPU FP32 master/m/v逐位等于同步CPUAdam，BF16设备权重逐位等于master转换结果。覆盖窗口尾块、帧交界与slot循环。
2. 首次尝试保留自定义分块BF16 backward，开始20步计划。前4步103.17/55.28/54.05/53.67秒；第5步两条独立验证loss为2.78272，第10步恶化为5.13942（初始2.88877）。主动停止，不把该组作为有效BF16精度基准。
3. 首步52,928坐标与旧FP32组比较，初始抽样权重差为0，但梯度相对L2约5.10e5；最后一层FFN的down/up梯度差仍较小，gate分支出现异常放大。该现象不解释成正常BF16舍入，更不据此认定BF16训练不可用。
4. 小尺寸及真实5120/17408、28-token的FFN分支测试，自定义反向与直接BF16 autograd的梯度相对L2约0.4%，开启CPU更新未改变该结果。该小测不能解释整模型异常。
5. 完整模型无更新诊断：同一首个训练样本FP32 loss=1.54175174，BF16 loss=1.54351318；末层SiLU反向与CPU解析式相对L2约6.27e-8。诊断包含不同执行顺序和同步采样，尚不能把差异唯一归因于某一个内核或同步问题。
6. 改为原生PyTorch BF16线性层自动求导，保留CPU FP32 master/Adam，使用临时BF16叶子权重的post-accumulate hook消费梯度；由autograd管理权重和激活生命周期。真实尺寸、单卡与跨卡FFN对照中，前向、输入梯度及全部被测权重梯度均与直接BF16 autograd一致，包含开启更新流水的情况。
7. 从原始checkpoint重新启动原生自动求导20步组；增加首步梯度检查、第4步完整验证和每5步独立验证异常停止条件。前一个组不接续训练、不作为新组初值。

后续原生双卡组首步因stream/event无效失败，未完成完整更新。修正回调设备上下文、串行提交及producer事件保活；双卡状态刷新小测与跨卡FFN再次通过，但不把这些小测当整模型稳定性证明。

单卡首版常驻计算权重约52.5 GiB，原生autograd仍复制当前线性层的BF16权重，首步反向额外申请2.37 GiB时OOM。随后改为直接在持久化BF16计算Parameter上自动求导，设备分帧只是同一块存储的视图，不再复制当前算子的BF16权重；梯度和权重仅按有界帧转FP32用于CPU更新。真实尺寸FFN的前向、输入梯度、全部权重梯度均与参考逐位一致，包含开启CPU更新。

当前从原始checkpoint重启的20步组为单张物理2号卡，CPU FP32 master/m/v；3号卡不放模型。该组同时改变反向实现和设备放置，与旧双卡FP32比较不能将速度差全归因于精度。

## 数据和比较方法

使用现有训练划分中按长度/哈希排序的20条不同短样本，长度28–84 tokens；前4条与旧FP32四步组相同。8条独立验证样本合计433个assistant token；训练不使用验证集或GSM8K。

速度比较使用相同前4条样本的第2–4步均值；后续样本逐渐变长，后5步均值仅描述本次运行。第4步FP32执行验证可对照旧FP32四步组；第20步验证是更长训练后的结果，不与四步组当作同训练量精度对照。小规模验证不能证明长期质量等同。

本轮性能/稳定性试验尚未保存新的完整模型checkpoint；原始模型文件保持不变。

## 完成结果

持久化BF16计算Parameter的单卡组已完成20次更新，进程正常退出（returncode=0）。每步更新全部26,895,998,464个文本参数，步末参数梯度均已释放。20条训练样本不重复，与验证哈希无交集。来源、逐步计时、参数覆盖、验证明细和源码哈希见[过滤证据](../../evidence/2026-10-24/bf16-master-training-results.json)。

| 指标 | 结果 |
|---|---|
| 实际模型设备 | 单张物理2号910B2；3号未放模型 |
| 前4步耗时 | 51.31 / 42.34 / 42.27 / 42.69 秒 |
| 相同第2–4步均值 | 旧双卡纯FP32 44.51秒；本次单卡混合精度42.43秒，耗时减约4.68% |
| 后5步均值 | 49.78秒，样本比前4步更长，不据此与旧4步直接比较 |
| NPU分配峰值 | 57.314 GiB；预留峰值57.824 GiB，不含驱动基础占用 |
| 主机RSS峰值 | 302.95 GiB；CPU持有FP32主权重和完整m/v |
| 原始checkpoint | 只读；本次未保存新的完整checkpoint |

BF16来自FP32 master转换，不需要另下载一个模型。但转换产生的计算张量仍占显存。本实现把它保留为计算缓存，CPU更新FP32 master后逐帧刷新；帧只是同一计算Parameter的视图，不额外复制当前层完整BF16权重。按层临时转换可减少常驻缓存，但会增加重复转换和搬运，本轮没有测该替代方案。

首步52,928个抽样坐标：初始权重差为0，旧FP32梯度L2=1.48041，本次=1.48365，梯度相对L2差约1.171%。这是混合精度计算差异，不是逐位相同；抽样不证明全部坐标。详见[梯度聚合诊断](../../evidence/2026-10-24/bf16-single-gradient-diagnostic.json)。

| 训练结果与验证执行方式 | 8条验证loss | assistant token正确数 / 433 |
|---|---:|---:|
| 原始主权重，FP32执行 | 2.056467 | 227 |
| 旧FP32训练4步，FP32执行 | 1.534962 | 263 |
| 本次混合精度训练4步，FP32执行 | 1.497234 | 261 |
| 本次混合精度训练20步，FP32执行 | 1.538380 | 266 |
| 同一20步主权重，BF16执行 | 1.531951 | 265 |

第20步两种执行方式仅差1个正确token；这衡量同一训练后主权重的执行舍入差异，不代表20步纯FP32训练与20步混合精度训练质量相同。旧纯FP32只有4步对照，8条验证也不足以评判长期质量。训练样本彼此不同，因此逐步训练loss不能直接当同一任务的收敛曲线。

速度差同时包含单/双卡放置、反向实现和计算dtype变化，不把4.68%全归因于BF16。此前自定义反向异常、原生双卡stream/event失败和单卡临时副本OOM均保留；本次单卡成功不证明原生双卡问题已完全解决。
