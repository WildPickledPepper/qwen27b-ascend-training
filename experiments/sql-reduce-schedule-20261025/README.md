# 固定256条更新的调度优化：107.97 → 101.28秒

本轮保留每256条更新一次、每卡micro16、累积8、同一批768条SQL训练样本及顺序、相同有效token/padding、BF16计算、CPU FP32主权重与Adam m/v。最终选择**有界CPU梯度接收队列 + 稍大的梯度归约在途窗口**，没有采用12GiB NPU梯度驻留，也没有改变更新频率。

## 同工作量的整模型结果

两张910B2，首256条预热，后两轮各256条取两rank较慢值再平均：

| 配置 | 秒/256条 | 是否选用 |
|---|---:|---|
| 原有micro16/global256参考 | 107.97 | 参考 |
| 12GiB NPU梯度驻留 | 126.66 | 否 |
| CPU累积、两接收槽 | 119.42 | 否 |
| CPU累积、32槽 | 108.56 | 单独未带来整体收益 |
| 32槽 + 扩大参数预取预算 | 109.03 | 否 |
| **32槽 + 梯度归约事件阈值2→4** | **101.28** | **是** |

选中配置后两轮101.1558、101.4104秒；相对原107.9709秒缩短**6.19%**，相对最近的32槽对照108.5618秒缩短约6.70%。短跑数据不代表长期训练或所有数据长度的通用提升。

第768条的同8条独立验证：loss **0.8581519723**，正确token **204/224**，与原配置一致。两rank、三次更新的小模型完整FP32梯度/master/m/v逐位一致；不将此扩展为整模型长训练的位级证明。FP32状态dtype/字节、有效输入/padding工作量、DeepSpeed配置与参考均已核对。

## 为什么这次有效

梯度归约和参数拉取都在训练流水里，但“通信累计多久”和“是否堵住计算”不同。对原生参考窗口按时间区间去重，AllGather未与计算重叠约10.62秒，ReduceScatter约15.58秒，归约是更大的暴露部分。

CPU累积先减少旧梯度回传，每rank梯度逻辑往返从484.13降到295.86GB，少38.89%。两个接收槽却使主线程每轮约17.5秒等槽；扩到32槽后降到约0.03秒，但CPU相加等工作抵消了局部收益，整轮仍约108秒。所以没有用“字节减少”或“等槽减少”宣称成功。

原生reducer源码会在事件队列超过阈值时同步等待，再继续提交后续归约/反向工作。安装环境实测`handles_memory_backpressure=False`，原阈值为2。选中版本只在实例内改为4；由于条件是`len(events) > limit`，记录队列上限由3变5。保留原生collective、事件、梯度相加顺序和Adam数学，给后续反向计算更多提前下发的空间；32个有界CPU接收槽负责接住后续数据，避免在另一处再次堵住主线程。

对比32槽对照与选中配置的**相同第4轮输入/padding**的rank0 Profiler：

| 时序证据 | 32槽、阈值2 | 32槽、阈值4 |
|---|---:|---:|
| AllGather次数 | 4721 | 4721 |
| ReduceScatter次数 | 4504 | 4504 |
| AllGather未与计算重叠 | 10.52秒 | 9.09秒 |
| ReduceScatter未与计算重叠 | 15.88秒 | 14.32秒 |
| 主机事件同步API累计 | 28.23秒 | 23.87秒 |

通信次数和参数字节没有变；改善来自时间安排与重叠。主机API范围含后台接收等待，且与其他范围重叠，**不能把这些秒数相加**。Profiler会改变执行开销，其窗口下降量不直接当作无采样测速。

训练段每卡allocated峰值仍约42.87GiB。选中采样中未记录到`aclrtMallocPhysical`/`aclrtFreePhysical`条目，没有重现12GiB驻留时各11289次的物理页API热点。allocated不是npu-smi总占用；保留内存池与驱动也占显存。

## 已核对但未采用的方向

- 大NPU梯度驻留省了复制，却挤压内存池、增加物理页管理开销，实际更慢。
- 原生参数协调器受`max_live - available`和预取bucket双重限制。将bucket从134,217,728改到最大层383,273,184元素，单独未改善整轮时间，不选。
- FFN leaf分组代码只作准备，在任何GPU子进程启动前取消。进一步拆分时序后发现归约暴露更大，而FFN父级回调可能延后梯度就绪，先处理已测到的在途约束。没有FFN分组实测成绩。
- 另有只读数据审计：固定每256条内部按长度重新组织，可使当前768条的padding工作量降低25.33%；它会改变微批分组，未在本轮上卡、不计入6.19%收益。

## 保存的配置与执行入口

- `selected-profile.json`：固定256/16/8、CPU32槽、原生归约事件阈值4及源码SHA256。
- `zero3-selected.json`：逐项等于成功运行的DeepSpeed配置，也与原生参考配置一致；调度变化由进程内适配器实现。
- `run_selected.py`：直接重放选中方案，默认3次更新，不再搜索或重跑其他候选；检查源码/配置哈希、2/3卡空闲、运行依赖与新输出目录。`--dry-run`只验证并显示参数。

激活原有服务器环境后，将模型/数据目录通过参数传入：

```bash
python run_selected.py --model "$MODEL_DIR" --data "$DATA_DIR" --output NEW_OUTPUT --steps 3
```

运行需要已验证的`CPU_ADAM_EXTENSION`、`VEOMNI_SOURCE`等环境变量。此配置的显存峰值是在当前SQL短样本上实测，max512是长度上限，并非micro16全512长度容量证明。原checkpoint只读，未保存新的完整模型。
