# 双卡张量并行评估

用户授权在完成流水线梯度卸载优化后评估TP。流水线2GiB梯度驻留已完成，固定256条达到85.09秒；TP仅顺序使用实时空闲2/3卡，不动其他任务/共享库/原checkpoint。

## 小模型兼容性门槛已通过

环境torch2.10.0+cpu、torch-npu2.10.0.post4、Transformers5.14.1、DeepSpeed0.19.8。本机Qwen3.5有14条HF TP规则，AutoTP可读取，普通注意力/FFN分片；GDN采用`colwise_gather_output`，投影权重分片后收齐激活，核心GDN计算在每rank保留完整。

实际小模型为4层（3 GDN + 1普通注意力），同一批数据TP2、DP1、micro16、累积16，原生ZeRO-1 CPU FP32主权重/Adam m/v，BF16计算/累积。输出与未切分模型比较，所有参数的重建梯度逐项比较，随后完成一次原生CPU优化器更新。正式路径关闭观察钩子，同样通过；这不是27B速度结果，也不是位级一致证明。

原生第一次检查被Q/K norm梯度差异拦下：每rank相对误差约64%–70%，两个rank相加后相对参考约1%，其余参数通过。注册状态和字典均显示钩子存在，但观察到实际回调0次；提前移动模型到NPU或读取前全设备同步均未解决。在优化器初始化结束后，仅对这些标记为TP梯度求和的共享参数重新调用公开`register_hook`绑定SUM回调，实际执行16次，全部梯度检查通过。不改共享安装，不放宽门槛。具体何处丢失回调连接尚未追到框架源码行，不能泛称所有DeepSpeed/Ascend版本都有该问题。

## 27B首次容量试验

原micro16/global256/48层选择性重算的TP2+ZeRO-1 CPU卸载，完成初始化/验证及第1个训练micro，在第2个前向OOM；尚无整步速度。失败日志和原入口保留，不能把未完成任务记作慢或快。

64层全部重算tiny通过，但27B仍在第2个前向OOM，已正常清理。进一步核对本机`stage_1_and_2.py`的`reduce_ready_partitions_and_remove_grads`：Stage1非累积边界不进入梯度归约/清理分支，CPU优化器卸载不等于每个micro的梯度都已离开NPU。局部模型参数14,085,021,184个，对应约28.17GB BF16梯度；初始allocated30.71GB，额外累计梯度足以耗尽可用空间。

改为原生ZeRO-2 CPU梯度卸载，恢复原48层重算、micro16/global256/原样本与padding。tiny实际检查第1个micro后NPU参数梯度storage为0、全部梯度检查通过；27B完成四轮，micro结束allocated约31–32GB稳定，正常轮allocated峰值最高61.33GB。原Stage1/all-recompute失败单列，不混入计时。

## 最终选择：保留优化流水线

相同原始768条、样本顺序、长度及padding，micro16、global256、48层选择性重算，BF16计算/累积，CPU FP32主权重和Adam m/v。前三轮正常训练，第一轮预热不排名；第四轮重复首256条，仅供双rank ms采样。

| 方案 | 两轮正常秒数/256条 | 均值 | 相对优化流水线 |
|---|---|---|---|
| 原ZeRO-3 | 见原归档 | 95.74秒 | — |
| 原两段流水线 | 92.97 / 97.64 | 95.31秒 | — |
| 流水线+每段2GiB梯度驻留 | 85.0948 / 85.0856 | **85.09秒** | 1.00倍耗时 |
| TP2+原生ZeRO-2 CPU卸载 | 192.3612 / 199.1368 | **195.75秒** | **2.30倍耗时** |

流水线按原顺序在NPU累积16次、末尾一次卸载，精确保序的小模型三步完整状态逐位一致，每卡少卸载32,212,254,720字节（2GiB×15）。这部分使旧流水线耗时减少10.72%。TP使用原生CPU梯度卸载，没有套用该FIFO与驻留缓存；本结果比较当前实际实现，不代表所有TP实现的上限。

## ms说明TP为什么慢

对第四轮Profiler DB只读聚合，按时间区间合并，避免重复相加。下表使用rank0；采样会扰动时长，不能用其208.97秒替换正常均值195.75秒。

| 采样指标 | 优化流水线 | TP2 |
|---|---:|---:|
| 设备任务窗口 | 91.94秒 | 208.97秒 |
| 计算任务覆盖 | 39.53秒 | 74.47秒 |
| 异步复制覆盖 | 15.23秒 | 45.27秒 |
| GDN `prepare_wy_repr_bwd_kernel` | 384次 / 累计4.97秒 | 768次 / 累计9.92秒 |
| GDN `chunk_fwd_kernel_o` | 768次 / 累计1.92秒 | 1536次 / 累计3.84秒 |
| MatMulV3 | 11520次 / 累计16.37秒 | 23088次 / 累计25.69秒 |

当前HF规则把GDN投影结果收齐，核心GDN计算每rank完整保留；调用次数和耗时证实了每卡重复计算，而非仅凭源码推断。两段流水线每卡只执行自己32层；TP每卡参与全部64层，GDN没有按两卡拆开。矩阵乘的局部分片也没有抵消这些额外工作。

TP每rank有15,733次AllReduce和7,680次AllGather；这里AllGather主要来自激活收齐，不应误写成ZeRO-3拉取完整权重。rank0通信累计37.07秒、区间覆盖37.01秒，其中36.24秒没有与计算重叠。通信事件包含等待，不能把它全部叫传输时间或带宽饱和。

TP rank0窗口互斥分解如下，合计208.97秒：计算74.47秒；无计算的通信36.24秒；既无计算也无通信的复制23.19秒；前三类之外的CPUAdam调用8.14秒；其余66.93秒。rank1相应为74.40 / 29.12 / 23.24 / 6.68 / 75.53秒。最后一类尚未逐事件归因，不能全部说成通信或CPU累积。DB没有复制方向字节表，45.27秒只称异步复制覆盖，不能全当CPU↔NPU传输。上述覆盖时间存在重叠，仅互斥分解允许相加。

可确定的结论是：这版TP增加了GDN重复工作、频繁激活通信和复制，尚不适合替换85.09秒流水线。此次没有继续扩展TP调参或额外训练。
