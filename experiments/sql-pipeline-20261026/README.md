# 两段流水线 + CPU FP32 AdamW

用户授权在实时空闲的物理2/3卡试验两段流水线，保持原固定256条训练口径、用ms工具分析并提交Git。默认95.7402秒/256条的ZeRO-3配置不改。

## 固定协议

前32层及嵌入放第一段，后32层、最终norm和输出头放第二段。每段只保存自己负责的BF16计算权重；FP32主权重、Adam一阶矩/二阶矩保留CPU，不量化、不改原checkpoint或共享安装。

全局batch256、micro16、原768条顺序及原两个数据rank的分组/padding、max512、原学习率和AdamW超参、48/64层选择性激活重算保持。原DP每rank8个micro，在PP中改为16个micro共同通过两段，仍每256条更新一次。使用同步1F1B，无延迟权重更新。只传阶段间激活和其梯度；裁剪前另做两段标量全局范数归约。

BF16梯度累积改为16个micro按顺序CPU累积，不再使用旧DP的分片归约树，因此不宣称与旧整模型逐位相同。比较同768条后的独立8条验证，并单列数值差异。原协议参考均值95.74024082010146秒/256条；前三更新首轮预热，后两轮取较慢rank平均；第四轮仅用于双rank Level1/Db采样。

## 最终结果：整体持平，不替换默认

正式运行正常退出，前768条三次更新及第4轮单独采样全部完成。训练工作量逐项核对：相同样本哈希/顺序/长度、相同原DP分组padding、每256条一次更新、全部26,895,998,464文本参数/851个张量、48/64层重算。两段CPU FP32 m/v共215,167,987,712字节，未量化。

| 固定256条，无采样 | 原ZeRO-3 | 两段流水线 |
|---|---:|---:|
| 第2轮，取较慢rank | 95.5825秒 | 92.9702秒 |
| 第3轮，取较慢rank | 95.8980秒 | 97.6413秒 |
| 后两轮平均 | **95.7402秒** | **95.3057秒** |
| 相对变化 | 参考 | 少0.4345秒，约0.454% |

两轮之间波动4.67秒，明显大于0.43秒平均收益；本次按持平处理，不声称有稳定加速。保留原`sql-boundary-overlap-20261025`默认入口及全部8项源码/配置哈希；该独立流水线实现也不代表PP训练的性能上限。

## 为什么省掉通信，整体却没有明显变快

按正常第2、3轮rank0主线程范围比较：

| 互不重叠的整步阶段 | 原ZeRO-3 | 流水线 | 变化 |
|---|---:|---:|---:|
| 前向、反向、梯度收尾及范数，至更新前 | 81.1214秒 | 74.6892秒 | 少6.4322秒 |
| 更新收尾 | 14.6099秒 | 20.6164秒 | 多6.0065秒 |

余下约毫秒级差异是阶段外记账。新更新范围包含CPU端BF16梯度转FP32、裁剪、原生CPUAdam和BF16回传，原方案在此前梯度收尾中已做一部分转换，不能把多出的6秒说成Adam数学内核本身慢6秒。

另一个关键变化位于反向内部：原来每张卡做8个micro、先归约并留下半份梯度；现在每段做16个micro、把自己全部参数的本地梯度送CPU。每段每轮提交约**430.34GB BF16梯度D2H逻辑字节**。CPU BF16加法范围由**26.86秒增至58.06秒**；主线程等待有界接收槽平均**43.53秒**，worker等待D2H生产者平均11.44秒。CPU加法、worker等待和主线程槽等待都与反向重叠，**不能加到上表再算一遍**。

队列为每段16个128MiB锁页接收槽，CPU BF16累积，梯度用后释放；未让整段梯度常驻NPU。它避免显存溢出，却把调度压力转移到CPU累积/卸载链路。结论是本实现中省掉的通信和其他处理收益，被新增CPU工作大体抵消；不能推导为“流水线并行无效”。

第一次小测因未切分对照模型的rotary缓冲区被整体`.bfloat16()`转换而出现差异；重建FP32 rotary后通过，失败日志保留在私有实验目录。没有放宽阈值来绕过该失败。

## 已排除的诊断运行

首版CPU范数版本跑完四轮并采样，但初始验证为1.0142586231、203/224，与旧方案1.0108281374、202/224不一致。`cpu-norm-diagnostic`证据明确标记`valid_for_speed_comparison=false`；其训练耗时只作为诊断，不能当同初始化的正式加速比较。随后NPU范数版本发现同样初始差异后，显式校验自身torchrun进程组并停止，没有触碰其他任务。

根因核对：原生zero.Init使rotary频率在NPU上计算，首版在CPU上计算后搬到NPU。两者均为FP32，但频率最大绝对差2.98e-8，BF16计算后初始验证可不同。`probe_rotary.py`在两张卡核对原生zero.Init/CPU/NPU构造：直接NPU构造与原生频率SHA256相同，逐位一致；CPU构造不同。最终入口显式在NPU构造rotary，单条验证也保留旧调用的不传attention_mask方式，并增加正式训练前验证保护；最终实测初始loss和正确token已与旧方案一致。

首版ms数据库还确认CPU范数范围21.95/27.65秒内无设备计算或复制；该实现代价已改为FP32 NPU范数后重新验证，不把它当流水线本身限制。新版本另外记录CPU梯度队列中等待复制与BF16累积的时间。梯度清零纳入整步计时，CPU FP32 Adam不变。
