# 梯度缓存尾部额外3.87秒：分段计时复核完成

2026-10-27。上次4/4→4/8GiB运行中尾部12.64→16.51秒被描述为抵消收益的增长，但那个计时包含CPUAdam、转换、回传与跨卡等待，不能建立缓存扩大的因果关系。本轮分段复测没有复现额外3.87秒：尾部13.1445→13.2172秒，仅多0.0728秒；整步80.6024→77.8298秒，少2.7726秒（3.44%）。旧原始结果保留，但撤回“缓存扩大必然造成尾部变慢”的解释。

## 训练和计时方式

物理3/4号910B2空闲时运行；Qwen3.5-27B文本全参、原SQL768条/global256/micro16/16micro/48层非重入重算、BF16计算及梯度累积、CPU FP32 master/m/v、512token连续化分块loss完全保持。两段同步1F1B自定义PyTorch/Transformers，CPU DeepSpeed CPUAdam组件。4/4和4/8各3步，第一步lr0预热、后两步平均。原入口与上轮副本不改，无profiler采集开销。

`train_timed.py`只插入host monotonic计时；每更新chunk计FP32梯度转换/裁剪、CPUAdam、双缓冲复用等待、锁页BF16转换、H2D调用、event记录，末尾event等待、device同步、barrier单列。保留每chunk详细行。各段和与旧组合timer差小于0.5秒，原训练数学与顺序不改。H2D调用时间是主机提交/阻塞时间，不是设备纯DMA时长；DMA可在CPU工作期间执行。

## 原来3.87秒的原因能确定吗

不能事后确定到具体子环节：旧日志没有上述分段计时。本轮确认额外3.87秒并不稳定复现，不能把它说成缓存扩容的固定开销，也不能把新结果冒充旧那次运行的细分。现场另观察到两组CPU内存均跨NUMA分布；没有旧运行对应记录或控制变量证明它导致历史差异，因此仅保留诊断线索，不作为根因结论。两组各两次正常更新仍不足以宣称长期稳定3.44%提升。

代码`run_sequence.py`负责两组、空闲检查及本组进程超时退出；`collect_results.py`核对源码SHA、数据/manifest/范数/验证和尾部计时覆盖。完整证据见[分段计时与每chunk数据](../../evidence/2026-10-27/sql-cache-tail-results.json)。本轮结束，不自动启动下一轮优化，原默认入口保持。
