# 流水线剩余瓶颈：复制流解耦

**最终采用原复制路径+每段4GiB保序梯度驻留：81.2160秒/256条，比2GiB版85.0902秒少4.553%。** 独立复制流当前实现87.9893秒未采用。剩余主要限制是CPU梯度累积和末尾更新/回传，下面保留定位、失败与验证过程。

2026-10-26用户授权继续优化85.09秒流水线，要求ms定位并估算剩余空间。固定原768条/顺序/padding、global256/micro16、16个流水线micro、48层重算、每段2GiB BF16梯度驻留、CPU FP32 master/m/v、原更新次数及累加顺序；只用实时空闲物理2/3卡，独立目录，不改共享库、原checkpoint或既有候选。

## 旧数据给出的具体机会

旧rank0 ms窗口91.94秒：计算覆盖39.53秒，未与计算重叠的通信10.19秒，既无计算也无通信的复制15.23秒，其他26.99秒。四类互斥，合计窗口；采样91.94秒不代替正常85.09秒。

计算与全部MEMCPY_ASYNC均在stream254，重叠为0。反向宿主范围内复制13.89秒，rank1为14.01秒；这支持独立D2H流重叠，而不是凭框架名称猜收益。该范围是与宿主反向区间的时间相交，不把异步设备事件强行当宿主调用的子节点。

正常rank0 CPU BF16累积51.22秒、等接收槽34.65秒，更新收尾约17.34秒；这些有重叠，不能相加。ms更新范围中rank0无设备任务14.93秒、rank1为15.80秒：优化复制不会自动消掉CPU Adam。通信事件也含等另一段的时间，不能把10.19秒全当链路传输瓶颈。

因此本次只针对反向复制串行：采样中约14秒是完全隐藏这部分复制的乐观上限，不承诺正常轮一定减少14秒，更不能宣称所有非计算时间都可消除。CPU累积及更新仍形成后续限制。

## 候选与验证门槛

梯度产生后，在主流记录ready事件，独立复制流等待它；固定16个锁页接收槽复用规则不变。源梯度通过`record_stream`保留到复制完成，CPU worker等每个复制事件、按原FIFO逐次BF16相加，再归还接收槽。全部micro结束仍先排空，再全局裁剪和更新，禁止提前更新权重。

小模型同时覆盖驻留及非驻留参数，连续三次完整梯度/master/m/v须与原流水线逐位一致；通过后才跑27B前三正常轮（第一轮预热）及第四轮ms采样。新采样增加等槽及CPU累积标记和逐参数时间计数；若worker标记没进入Profiler，报告缺失，不当零耗时。

小模型独立首步检查及三次完整状态逐位门槛均通过，随后`run_sequence.py`完成27B正式四轮。`diagnose.py`对旧DB只读分析，SQL与过滤证据见[旧流水线分解](../../evidence/2026-10-26/sql-pipeline-overlap-before.json)、[三步状态门槛](../../evidence/2026-10-26/sql-pipeline-overlap-state-comparison.json)、[独立首步校验](../../evidence/2026-10-26/sql-pipeline-overlap-smoke.json)。

## 独立复制流完成：不采用

正常两轮87.9903/87.9882秒，均值87.9893秒，比原85.0902秒多约3.41%。四轮输入/长度/padding、驻留选择、D2H字节、梯度范数与训练后短验证全部精确核对，原8项基线哈希保持。任务和采样正常退出。

新rank0 ms计算39.57秒（旧39.53），复制流1090、计算流1088，确实产生5.999秒计算/复制重叠；无计算/通信的复制15.23→9.44秒。但其他区间26.99→34.35秒，抵消这部分重叠。`gradient/slot_wait`宿主标记共30.94秒，其中7.52秒没有计算/通信/复制任务；rank1相应27.39秒与10.14秒。CPU worker累积标记未进入Profiler，明确记缺失；普通计时器rank0累积51.22→55.55秒、等槽34.65→37.55秒，不能把增加的4.33秒全归为某个未测的原因。

已证实的结论：只解决设备复制串行，未解决CPU消费接收槽的限制，当前实现没有整步收益。没有宣称侧流失效、带宽饱和，或把全部其他区间都归到CPU。见[正常结果](../../evidence/2026-10-26/sql-pipeline-overlap-async-results.json)、[新ms区间](../../evidence/2026-10-26/sql-pipeline-overlap-after-async.json)。

该候选正常轮也执行新增标记包装，CPU计时包含这些包装，未独立隔离其开销；本次未采用的是当前实现，不能据此认定独立复制流原则无效。

## 根据CPU接收端证据，下一项为4GiB驻留

恢复已锁定的原复制入口，只改变既有驻留预算2→4GiB，继续保留全部FP32状态和原梯度累加/更新边界。按旧四轮真实峰值估算，rank0新增2GiB后allocated约60.73GB，reserved加实测卡基础占用后仍留约1.80GB；6GiB则超过保守物理预算，排除。此容量预测不保证所有新输入都能放下，正式轮需核对实际峰值。见[容量与精确字节计划](../../evidence/2026-10-26/sql-pipeline-overlap-capacity-plan.json)。

多驻留2GiB每轮每卡精确少32,212,254,720字节D2H及相应CPU BF16加法输入。`run_cache4.py`先用更大tiny预算覆盖驻留/非驻留路径，完整三步状态逐位通过后，完成相同27B前三正常轮+第四轮ms。

## 4GiB实测：81.22秒，采用

| 正常指标 | 2GiB旧版 | 4GiB新版 |
|---|---:|---:|
| 第2轮较慢rank | 85.0948秒 | 80.2020秒 |
| 第3轮较慢rank | 85.0856秒 | 82.2300秒 |
| 均值/256条 | 85.0902秒 | **81.2160秒** |
| rank0 CPU BF16累积 | 51.2234秒 | 47.2295秒 |
| rank0接收槽等待 | 34.6504秒 | 32.8180秒 |
| rank0反向/排空前缀（含前向） | 66.3273秒 | 63.3675秒 |
| rank0更新回传尾部 | 17.3433秒 | 16.4269秒 |
| 每卡梯度D2H逻辑量 | 398.1236GB | 365.9114GB |

整步平均少3.8742秒（4.553%）；两轮都快于旧版，但仅两轮稳态，不宣称长期吞吐。CPU相加少3.9939秒，不把该值与整步收益或槽等待重复相加；Adam数学和实现没有变化，尾部计时减少不单独归功于Adam内核优化。

### ms核对收益及剩余瓶颈

rank0采样窗口91.9351→87.0941秒，计算39.5266→39.5604秒，未与计算重叠的通信10.1898→7.2772秒，独占复制15.2295→14.1232秒，其他26.9892→26.1333秒；互斥四类相加等于窗口。通信仍含等另一段的时间，不称链路带宽提升。模型参数、输入和训练更新数没减少，NPU计算覆盖基本不变，减少的是梯度卸载/CPU累积工作和相关等待。

新版rank1计算覆盖41.5685秒。rank0反向宿主范围里仍有12.7421秒复制和9.3592秒无设备任务；rank1为12.8525秒和8.6344秒。当前原复制路径仍无计算/复制重叠。但独立复制流试验已证明“增加重叠”不足以消除CPU接收槽限制，不能将这些区间全写作可直接回收时间。

更新期间rank0有14.0204秒、rank1有15.0981秒没有计算/复制/通信任务；结合显式`optimizer/CPUAdam_and_return`范围和源码，说明末尾CPU更新/准备BF16回传的尾部仍明显。Profiler没有捕获worker CPU累积范围，用正常轮直接计时47.2295秒佐证，不用缺失标记虚构0秒。

### 还有多少空间

用正常轮、同rank的两个不重叠范围计算：CPU梯度相加47.2295秒，在`off.finish/drain`结束后才能开始更新回传16.4269秒。**如果这两段耗时保持不变**，即使把其他所有工作/等待都理想化隐藏，仍至少63.6564秒；相对81.2160秒，乐观调度空间为17.5596秒、21.62%。这没有把Profiler的87.09秒混进正常计时。

这是当前代码、当前测量成本下的条件估计，不是910B2物理上限，也不保证能跑到63.66秒。想继续明显突破，需要减少/加速CPU梯度累积或FP32更新本身；仅隐藏复制不够。额外驻留已受约1.8GB保守余量限制，不能无约束增加缓存。见[可复算的空间估计](../../evidence/2026-10-26/sql-pipeline-overlap-headroom.json)。

### 数值、资源及重放

4GiB两rank各选29个完整参数、实际4,294,967,296字节。四轮D2H精确减少`2GiB×15`，原样本哈希/顺序/长度/padding、851个原参数形状、48层重算、更新边界、CPU FP32状态字节、四轮梯度范数及训练前/后短验证全部核对通过。768条后loss0.8551014662、205/224正确token，与2GiB版精确相同；不据8条短验证推断长期质量等价。

rank0实际allocated峰值约60.731GB，rank1约58.041GB，与容量预测一致。训练/采样均正常退出，2/3卡无运行进程，其他任务未操作，原ZeRO-3的8项源码/配置哈希和2GiB锁定入口保持。

已封存[selected-profile.json](selected-profile.json)及[重放入口](run_selected.py)，`--dry-run`核对三项LF源码哈希、不启动训练。`train_resident.py`与实测使用的原入口源码相同，仍依赖原独立CPUAdam/VeOmni环境；只传新输出目录，支持3轮正常或第4轮采样。旧2GiB版继续保留。
