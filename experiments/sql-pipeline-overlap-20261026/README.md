# 流水线剩余瓶颈：复制流解耦

2026-10-26用户授权继续优化85.09秒流水线，要求ms定位并估算剩余空间。固定原768条/顺序/padding、global256/micro16、16个流水线micro、48层重算、每段2GiB BF16梯度驻留、CPU FP32 master/m/v、原更新次数及累加顺序；只用实时空闲物理2/3卡，独立目录，不改共享库、原checkpoint或既有候选。

## 旧数据给出的具体机会

旧rank0 ms窗口91.94秒：计算覆盖39.53秒，未与计算重叠的通信10.19秒，既无计算也无通信的复制15.23秒，其他26.99秒。四类互斥，合计窗口；采样91.94秒不代替正常85.09秒。

计算与全部MEMCPY_ASYNC均在stream254，重叠为0。反向宿主范围内复制13.89秒，rank1为14.01秒；这支持独立D2H流重叠，而不是凭框架名称猜收益。该范围是与宿主反向区间的时间相交，不把异步设备事件强行当宿主调用的子节点。

正常rank0 CPU BF16累积51.22秒、等接收槽34.65秒，更新收尾约17.34秒；这些有重叠，不能相加。ms更新范围中rank0无设备任务14.93秒、rank1为15.80秒：优化复制不会自动消掉CPU Adam。通信事件也含等另一段的时间，不能把10.19秒全当链路传输瓶颈。

因此本次只针对反向复制串行：采样中约14秒是完全隐藏这部分复制的乐观上限，不承诺正常轮一定减少14秒，更不能宣称所有非计算时间都可消除。CPU累积及更新仍形成后续限制。

## 候选与验证门槛

梯度产生后，在主流记录ready事件，独立复制流等待它；固定16个锁页接收槽复用规则不变。源梯度通过`record_stream`保留到复制完成，CPU worker等每个复制事件、按原FIFO逐次BF16相加，再归还接收槽。全部micro结束仍先排空，再全局裁剪和更新，禁止提前更新权重。

小模型同时覆盖驻留及非驻留参数，连续三次完整梯度/master/m/v须与原流水线逐位一致；通过后才跑27B前三正常轮（第一轮预热）及第四轮ms采样。新采样增加等槽及CPU累积标记和逐参数时间计数；若worker标记没进入Profiler，报告缺失，不当零耗时。

目前状态：小模型独立首步检查及三次完整状态逐位门槛均通过，`run_sequence.py`已启动27B正式四轮；尚不宣称收益。`diagnose.py`已对旧DB只读分析，SQL与过滤证据见[旧流水线分解](../../evidence/2026-10-26/sql-pipeline-overlap-before.json)、[三步状态门槛](../../evidence/2026-10-26/sql-pipeline-overlap-state-comparison.json)、[独立首步校验](../../evidence/2026-10-26/sql-pipeline-overlap-smoke.json)。

## 独立复制流完成：不采用

正常两轮87.9903/87.9882秒，均值87.9893秒，比原85.0902秒多约3.41%。四轮输入/长度/padding、驻留选择、D2H字节、梯度范数与训练后短验证全部精确核对，原8项基线哈希保持。任务和采样正常退出。

新rank0 ms计算39.57秒（旧39.53），复制流1090、计算流1088，确实产生5.999秒计算/复制重叠；无计算/通信的复制15.23→9.44秒。但其他区间26.99→34.35秒，抵消这部分重叠。`gradient/slot_wait`宿主标记共30.94秒，其中7.52秒没有计算/通信/复制任务；rank1相应27.39秒与10.14秒。CPU worker累积标记未进入Profiler，明确记缺失；普通计时器rank0累积51.22→55.55秒、等槽34.65→37.55秒，不能把增加的4.33秒全归为某个未测的原因。

已证实的结论：只解决设备复制串行，未解决CPU消费接收槽的限制，当前实现没有整步收益。没有宣称侧流失效、带宽饱和，或把全部其他区间都归到CPU。见[正常结果](../../evidence/2026-10-26/sql-pipeline-overlap-async-results.json)、[新ms区间](../../evidence/2026-10-26/sql-pipeline-overlap-after-async.json)。

## 根据CPU接收端证据，下一项为4GiB驻留

恢复已锁定的原复制入口，只改变既有驻留预算2→4GiB，继续保留全部FP32状态和原梯度累加/更新边界。按旧四轮真实峰值估算，rank0新增2GiB后allocated约60.73GB，reserved加实测卡基础占用后仍留约1.80GB；6GiB则超过保守物理预算，排除。此容量预测不保证所有新输入都能放下，正式轮需核对实际峰值。见[容量与精确字节计划](../../evidence/2026-10-26/sql-pipeline-overlap-capacity-plan.json)。

多驻留2GiB每轮每卡将精确少32,212,254,720字节D2H及相应CPU BF16加法输入。`run_cache4.py`先用更大tiny预算覆盖驻留/非驻留路径，完整三步状态逐位通过后，才运行相同27B前三正常轮+第四轮ms。目前刚启动该顺序验证，尚无速度结论。
