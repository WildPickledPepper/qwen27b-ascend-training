# 双卡训练吞吐优化：2026-10-25

用户要求尽可能提高两张910B2的训练收益。沿用ZeRO-3原生BF16计算、CPU分片FP32主权重与Adam m/v，原checkpoint只读，不量化状态，不修改共享库。

## 比较口径

旧单卡42.43秒是每次更新1个样本的旧实现。上一轮标准ZeRO-3在相同全局batch=2时，单卡62.49秒、双卡41.64秒，已是1.50倍吞吐。不能直接把42和41相除判断双卡收益。

本轮先固定全局batch=32，测试每卡microbatch=4/8/16，梯度累积次数分别4/2/1。每组从同一原始权重开始，3次更新，每次使用相同32条训练数据、相同样本在同一rank，共96次样本曝光；序列28–125 token，独立8条验证，未使用GSM8K。每次2377个有效输入token，padding另外统计。

局部loss按全局有效assistant token数加权，确保不同microbatch与rank的梯度权重一致。BF16批处理/累积仍可能产生舍入差异，不承诺逐位一致。固定batch=32的各组可以比较吞吐；与旧batch=2不同的更新频率分开报告。

计时取两rank中较慢的一方，排除首个冷启动更新与有Profiler的更新。前向/反向/step为宿主墙钟阶段，异步任务的重叠由Profiler另查，不当纯设备时间。

## 优化顺序

1. 用较大microbatch减少重复前后向、权重收集及梯度处理；保持有效batch与数据相同。
2. 尝试关闭激活重算，若容量不足则仅关闭每四层中的一层，共48/64层仍重算。通过层标志核对实际配置。
3. 两rank仍各12个CPU核心，分别优先在NUMA4/5分配内存；preferred允许容量不足时回退，按匿名页驻留统计核对，不能仅凭绑核宣称本地化。
4. 利用容量提高ZeRO预取/存活参数预算及FP32更新分组，减少小组调度；合并测试只能归因于这组配置，不能拆成单项因果结论。
5. 最优配置单独采rank0 Profiler DB，先检查正常Stop与DB导出，再用只读SQLite执行技能CTE；采集组不参与无采样速度排名。
6. 最后按旧batch=2、4更新、相同8条训练样本补测，关闭重算并采用胜出的CPU/ZeRO配置，验证小批量的更新延迟收益。

完全关闭重算在microbatch16时OOM；失败保留。microbatch1最初完成一个冷启动更新后，第二步约600秒时出现rank1 SIGSEGV；同时有faulthandler定时栈输出，根因未确认。后续入口去掉定时dump，保留异常处理，成功组未把该失败计入稳态排名。

## 复现与证据

入口`train_throughput_v2.py`用于固定批量比较，`train_advanced.py`用于重算/NUMA/预取与Profiler，`run_sweep2.py`、`run_advanced.py`、`run_matched.py`依次单任务运行。`MODEL_DIR`、`DATA_DIR`、`CPU_ADAM_EXTENSION`指定本机现有资源；物理2/3卡可见，环境需提供匹配torch-npu/CANN/DeepSpeed。

原CPUAdam二进制只在进程中复用；保留此前有界梯度转换适配，不删除旧JIT缓存锁。每组记录源码SHA256、训练/验证哈希、每步状态字节、分配/保留显存、验证loss及token正确数。`collect_results.py`导出过滤证据，`analyze_profile.py`验证并查询rank0采样。

## 固定全局batch=32的结果

以下均为每组3次更新中后2次均值，取两rank较慢时间。首个更新单独保留在JSON。

| 配置 | 秒/更新 | 有效输入token/s | 每卡最大分配峰值GiB | 最终验证loss |
|---|---:|---:|---:|---:|
| 每卡4，全部重算 | 93.16 | 25.51 | 35.77 | 1.447393 |
| 每卡8，全部重算 | 58.81 | 40.42 | 35.77 | 1.446578 |
| 每卡16，全部重算 | 43.62 | 54.50 | 35.77 | 1.446561 |
| 每卡16，48/64层重算 | 42.46 | 55.98 | 46.38 | 1.446561 |
| 加NUMA4/5优先分配 | 39.45 | 60.25 | 46.38 | 1.446561 |
| 加大更新分组/预取预算 | 37.60 | 63.22 | 50.50 | 1.446561 |
| CPU各24核，保持上述配置 | 34.88 | 68.15 | 50.50 | 1.446561 |

减少重算的结果相对较小；CPU分配和更新/预取配置继续减少整步时间。NUMA匿名页抽查显示rank0约80 GiB在节点4、rank1约92 GiB在节点5，但两者仍有约64–70 GiB在节点6，不能称为完全就近分配，也不能把匿名页逐一认作m/v。

## Profiler核对

用`mindstudio_profiler_data_check`核对rank0 PyTorch采样的正常Stop元数据与DB导出。当前没有配置msprof_mcp，使用`ascend-profiler-db-explorer`的原始CTE及只读SQLite；`TASK`字段查技能文档，文档不含`PYTORCH_API`时才用PRAGMA补充。

采集手动从RECORD停止时出现调度警告，保留记录。采集更新墙钟40.983秒，设备TASK窗口41.004秒，差0.021秒；正常Stop与DB存在，计算/通信/用户范围均非空。整组有采样，排除吞吐排名。

| rank0采样指标 | 数值 | 含义 |
|---|---:|---|
| CPUAdam用户范围 | 44次，共11.170秒 | 包裹原C++更新本体，不改变算法 |
| 计算算子累计 | 144,031次，共6.590秒 | 跨流可能重叠 |
| 计算区间去重覆盖 | 6.338秒 | 合并计算算子时间区间，非整卡利用率 |
| MatMulV3累计 | 1,443次，共1.767秒 | 当前不是之前推理解码的口径 |
| AllGather累计 | 857次，共3.180秒 | 包含实际等待，非纯传输带宽 |
| ReduceScatter累计 | 563次，共3.148秒 | 不能直接与其他项目相加 |

Mul/ViewCopy/Slice/Cast等小算子数量很多，计算覆盖明显小于整步窗口。现阶段有CPU Adam、数据复制/梯度处理、通信及小任务调度开销，不能把整个差额都称为HBM搬运或某一个Python循环；无stack/shape采集也不能凭本组数据将每个小算子归到具体模块。

安装的torch-npu接口说明确有`npu_chunk_gated_delta_rule`，但写明支持推理场景，不能直接拿来替换需要梯度的训练路径。未修改共享库、未用推理算子静默替代反向计算。

CPU增核组从每rank12核变为24核，总计24→48个不同核心，不能把这部分收益称为单纯增加NPU的收益。与microbatch4同有效批量相比吞吐约2.67倍，与microbatch16最初配置相比约1.25倍。较大预取组和增核组每卡最大分配峰值约50.50 GiB，保留池显存另见JSON。

最优CPU24配置补采：39.114秒训练计时、39.139秒TASK窗口，正常Stop/DB校验通过。CPUAdam仍44次，累计9.729秒，较12核的11.170秒下降；计算算子仍144,031次、累计6.519秒，区间去重覆盖6.268秒。AllGather/ReduceScatter累计3.349/3.145秒，包含等待且与其他阶段可能重叠，不相加凑整步。独立无采样速度34.88秒不换成这次有采样计时。

## 原batch=2口径的最终复测

使用原来相同8条短训练样本、相同4次更新、相同初始权重及超参，逐条哈希核对通过。每卡1样本，不靠增大有效batch制造更新延迟收益。采用较大预取/更新分组、NUMA优先分配、每rank24核，并完全关闭激活重算；该小批量容量足够，64层实际重算标志均为0。

| 同全局batch=2 | 第2–4步秒/更新 | 有效输入token/s | 验证loss | 正确token |
|---|---:|---:|---:|---:|
| 历史单卡 | 62.49 | 1.157 | 1.504420161 | 263/433 |
| 历史双卡 | 41.64 | 1.737 | 1.504420161 | 263/433 |
| 本轮双卡优化后 | **30.13** | **2.400** | **1.504419923** | **263/433** |

四步分别56.281/30.007/29.995/30.403秒，首步不计稳态均值。相对原双卡吞吐1.382倍、更新时间减少约27.62%；相对之前单卡实现为2.074倍，包含CPU24→48核及执行配置改善，不是纯双卡扩展效率。每卡分配峰值40.49/40.67 GiB，保留峰值48.62/48.55 GiB。最终验证loss与原组差−2.38e−7，正确token相同。

## 结束与交付

共10组成功完整结果，另保留全关重算OOM和microbatch1的SIGSEGV失败。所有更新的FP32 m/v总字节始终215,167,987,712，主权重也是FP32；未量化优化器状态。`verify_results.py`核对相同batch32训练曝光、batch2与历史数据/更新次数、验证集分离及状态容量。

2/3卡自己的进程均正常退出，复核无活动进程、基础HBM3416/3415 MiB，未停止其他卡服务。原权重只读，没有保存新的完整模型checkpoint，没有自动Git提交/推送。
