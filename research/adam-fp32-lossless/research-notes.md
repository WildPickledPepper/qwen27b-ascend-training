# Adam FP32 状态与 BF16 权重的无损存储研究

日期：2026-10-23。范围：文献、仓库记录、位表示推导和 CPU 固定标量检查。没有运行训练、模型、反向传播或 NPU 测试；没有修改或推送训练仓库。

## 结论与证据边界

1. FP32 Adam 的 m/v 不是 BF16 扩展值，低 16 位不能默认空闲。即使输入梯度可被 BF16 精确表示，乘上 Adam 系数后也能产生非零低位。非零不等于不可压缩，仍需真实状态分析。
2. 正常有限 v 的非负性可以省符号位；指数的集中性可以提供统计冗余。没有发现能让本模型长期训练中的两份 FP32 状态必然压到一份 FP32 空间、同时逐位恢复的关系。
3. BF16 权重的指数编码有更直接的已有工作；Ascend 910B2 上也有权重无损压缩文献。但推理权重压缩、checkpoint 压缩不等于在线训练显存已经下降。
4. FP32 主权重是实现选择，不能对所有 BF16 训练额外计入。若同时保留主权重和其 BF16 转换副本，二者存在确定性冗余，值得单独消除。
5. 本地没有真实 Qwen m/v 转储，无法报告其熵、实测压缩率或速度。当前没有证据支持约 3.34 倍的无损状态压缩目标，也没有证明所有可能编码均达不到该目标。

## 仓库与容量基准

训练仓库检查版本 f98725d。当前成功基线是冻结 BF16 主模型、训练 4,456,448 个 FP32 LoRA 参数；全参训练尚未开始。不能把全模型 m/v、梯度或 FP32 主权重算成现有 LoRA 基线的实际常驻开销。

以下是未来全参训练的静态预算，文本可训练参数 N=26,895,998,464，单位 GiB=2^30 字节。未包含激活、通信、分配器、临时转换和压缩工作区。

| 项目 | 每参数字节 | 总量 GiB |
| --- | ---: | ---: |
| BF16 文本权重 | 2 | 50.10 |
| BF16 梯度（若如此存储） | 2 | 50.10 |
| FP32 m | 4 | 100.20 |
| FP32 v | 4 | 100.20 |
| 可选 FP32 主权重 | 4 | 100.20 |

m/v 合计 200.39 GiB；压到合计 60 GiB 需要约 3.34 倍、每参数一对状态约 19.16 位，且尚未计编码开销。这是合计预算，不能在没有分片方案时直接除以卡数。普通数据并行会复制许多状态。

仅去掉 v 符号位：64→63 位，理想节约 1.5625%。如果保留 m 符号和两份 23 位 fraction，即使两份指数完全免费，也仍有 47 位，理想约 1.36 倍、147.16 GiB。这个限制只针对“只压指数、其他位原样保留”的编码类别，不是所有无损编码的下界。

## m/v 的可逆编码方向

FP32 的位字段为符号 1、指数 8、fraction 23。正常有限 Adam 状态、v 从正零初始化、0≤β2<1 时，v 没有负数；若要求保留任意 NaN payload、负零等特殊位串，必须设异常路径。

候选方法包括块内指数前缀/差分、指数联合编码、位平面变换、确定性整数预测后 XOR 残差编码。预测不准只应影响压缩率，不能影响恢复；块头、码表、异常、对齐和原样回退必须计入。m 可因梯度抵消接近零，而 v 仍较大，不能由 m 精确推出 v。FP32 浮点减法残差再相加也不自动逐位可逆，宜优先考虑整数位操作。

时间差分若需要上一份完整状态作为基底，基底也占空间；不能只计算 delta 大小。初始 m=v=0 或 BF16 刚扩展到 FP32 时的高压缩率不代表长期训练。每位的边缘熵高，也不能单独证明联合编码无效。

CPU 脚本在 m0=v0=0、梯度 g=1（BF16 可精确表示）时得到 m 位串 0x3dcccccd、v 位串 0x3a83126f，低 16 位均非零。它采用显式分别舍入的 FP32 乘法，不是 Ascend 融合 Adam 的等价性验证。

## BF16、FP32 主权重与计算精度

需要区分参数持久存储、算子执行 dtype、梯度存储、m/v 存储。普通 FP32 训练只需 FP32 参数；常见原生 AMP 保留 FP32 参数，在适合的算子执行时转换低精度。某些框架则长期保留 BF16 参数及 FP32 主权重。显式 BF16 参数的训练也可以不保留 FP32 主权重，但小更新舍入和状态 dtype 需要另行处理。不能仅看 bf16=true 就推断全部张量布局。[PyTorch AMP 文档](https://docs.pytorch.org/docs/2.14/amp.html)、[DeepSpeed 配置](https://www.deepspeed.ai/docs/config-json/)

BF16 在 1 附近相邻值间距约为千分之几。若权重为 1，每步减去 0.0001，再立即以 BF16 最近偶数舍入写回，结果仍是 1，重复同样操作不会累积。FP32 持续保存更新后的值时，这些小改变量能够累积，供计算使用的 BF16 版本稍后再跳到下一个可表示数。[Mixed Precision Training](https://arxiv.org/abs/1710.03740)

如果参考实现同时常驻 W32 和 W16=cast(W32)，原始占 48 位/参数。只常驻 W32、按块转换 W16 可以保持参考值，但要评估转换成本、缓存和峰值。它最多先省掉 16 位重复副本，而不是免费删除 W32 的精度。

若直接存 W32 高16位和低16位，总计32位，可精确重建主权重，但高16位对应截断转换，未必等于参考实现的最近偶数舍入 BF16。

对有限 FP32 位串 U=(H<<16)|L，最近偶数舍入的 BF16 位串为 B=H+c（按16位模运算），其中 c=(L>0x8000) 或 (L==0x8000 且 H 为奇数)。存 B、L、c 共33位可以重建 H=B-c。固定示例 0x3f7f8000 和 0x3f808000 有相同 B=0x3f80、L=0x8000，但 H 不同，所以 B 加原始低16位并不总能唯一恢复。非 tie 情况可推导 c，tie 可以用异常信息处理；尚未实现通用压缩格式。NaN、subnormal、设备 flush-to-zero 和真实转换规则需要明确。

理想位打包 48→33 位时，本例文本权重组合 150.29→103.33 GiB，省约46.97 GiB；这是有条件的格式预算，尚不含打包开销，也没有 NPU kernel。若基线原本只存 BF16，则没有这份重复信息可供消除。

## 相关工作及适用范围

### 仅常驻一份 FP32 参数时的压缩

按用户澄清，目标布局是一份 FP32 参数，计算时按需转换 BF16，不预设完整 BF16 副本长期常驻。此时待压缩的是约100.20 GiB文本 FP32 权重本身，不能再把“消除完整 BF16 副本”计为已有布局的收益；计算缓存仍计入峰值。

若 FP32 参数由 BF16 checkpoint 直接扩展而来，初始化的每个有限权重低16位为零，保存其 BF16 原始位串即可精确恢复扩展 FP32，原始payload可从32位降到16位。它没有恢复 BF16 checkpoint 发布前可能已经舍弃的精度。经过 FP32 更新后，不再有低16位全零保证，不能继续只存16位并宣称无损。

对于具有完整 FP32 fraction 的普通权重，ZipNN 报告典型体积节约约17%；映射到本例约100.20→83.17 GiB。这是外部数据的预算示例，不是本模型实测或训练全程承诺。ENEC 在 Ascend 的若干 FP32 模型报告约1.15倍压缩，也属于权重推理场景。

候选在线布局：常驻压缩位流，读取一个块时恢复参数并生成计算所需 BF16；优化器阶段恢复该块的完整 FP32 参数、按原算术更新、重新编码。不能保留完整解压 FP32 副本再把压缩副本算作显存节约。更新的调度要保持前向、反向及重计算需要的参数版本。应验证训练更新后不同阶段的编码大小、原样回退和工作区峰值。

| 工作 | 支持的结论 | 不能直接推出 |
| --- | --- | --- |
| [ZipNN](https://arxiv.org/html/2411.05239v1) | 浮点指数分布及“低精度扩展 FP32”的零位有压缩价值；有训练 checkpoint 案例 | 本模型稠密 FP32 m/v 的压缩率 |
| [NVIDIA nvCOMP checkpoint 实测](https://developer.nvidia.com/blog/?p=115453) | 表2中 FP32 momentum 约1.06–1.07倍、variance约1.10–1.11倍；BF16权重更易压缩 | 专用联合编码上限，或在线训练显存和 Ascend 速度 |
| [DFloat11](https://arxiv.org/html/2504.11651) | BF16 模型权重无损指数编码，报告约30%体积缩减及 GPU 按块解码 | 本模型本地实测；训练或 Ascend 现成支持 |
| [ENEC](https://arxiv.org/html/2604.03298v2) | Ascend 910B2 上权重指数编码和解码；报告 BF16 权重约1.35–1.37倍 | FP32 Adam 在线压缩实现 |
| [LCT](https://arxiv.org/html/2610.22179v1) | BF16 张量在线无损压缩、解码与更新的训练设计 | FP32 m/v 同样压缩率；Ascend 已适配 |
| [FlashOptim](https://arxiv.org/html/2602.23349) | 主权重 splitting 与低位修正已有直接相关工作 | 默认24位权重或8位状态符合严格逐位无损要求 |

特别核对 FlashOptim：其高低16位切分能恢复 FP32，但改变 BF16 舍入方式；论文§4.4的16位修正方案对 BF16 仅报告99.92%的逐位重建，不能把“32位语义”或“训练质量相当”写成所有值100%无损。

权重压缩的参考预算：按仓库加载的 BF16 文本加冻结视觉模型约50.96 GiB，若假设达到 DFloat11 报告的30%缩减，可省约15.29 GiB，尚未扣工作区。这只是外部结果的预算映射。冻结 LoRA 主模型可压缩一次；全参训练则必须重新编码变化的权重，并处理反向及重计算对旧版本权重的依赖。

## 后续不启动训练也能做的验证

若已有允许读取的 optimizer checkpoint，可离线统计跨层、跨步 m/v 的指数直方图、联合/条件熵、位平面与低位零比例，并直接测编码字节数。没有现成状态就保留未知，不启动训练来补数据。

对候选格式验证 encode→decode 的 uint32 逐位一致，覆盖有限值、零、subnormal、边界和异常回退；单独核算持久 payload、码表、异常、块索引、分配预留、解码工作区及是否仍留整份原始副本。完整训练数值等价还要求更新运算顺序和融合规则保持参考行为，存储可逆本身不证明融合运算等价。

本目录脚本及 JSON 仅记录固定 CPU 位检查与静态容量计算，不包含真实训练压缩率或收敛结论。

## 利用已有权重精确恢复状态：首轮排查

用户进一步确定研究方向：梯度即用即弃，尝试由已有权重等信息精确恢复状态。新的目标是 m/v 合计30 GiB，意味着200.39/30≈6.68倍；平均每参数一对状态9.58位，包括元数据。即使一份状态完全免费恢复，另一份原始 FP32 状态仍有100.20 GiB，需要继续缩减。

### 相邻权重反解的代价

先忽略权重衰减，采用实数算术，令 c1=1−β1^t、c2=1−β2^t、Δ=W_{t−1}−W_t，则 Adam 更新关系可重排为：

    m_t = c1 * (Δ / η) * (sqrt(v_t / c2) + ε)

这只是理想算术恒等式。它需要上一份权重；如果额外保留完整上一份 FP32 权重，会增加约100.20 GiB。改存权重差也不能默认免费，并且 FP32 权重写回舍入会丢失更新信息。AdamW还需按具体更新算术处理权重衰减，不能把实数等式重排当成逐位等价。

`state_reconstruction_checks.py` 只执行固定 CPU 标量算术检查，没有模型或训练。采用明确的分别舍入 FP32 运算，t=1、W0=1、η=1e−4、ε=1e−8、β1=.9、β2=.999：

| 输入或保留信息 | 检查结果 |
| --- | --- |
| g=±约1e−13 | 新W均为1、v位串相同，m分别为正负约1e−14 |
| 两个相邻FP32 g | 新W和m位串相同，v位串不同 |
| 固定m及两个相邻v，计算归一化比值 | 相同FP32比值可以对应不同v |

这些碰撞排除了“只凭相邻权重加v就始终精确还原m”“只凭相邻权重加m就始终精确还原v”等指定反解器，也说明单独保留比值不必然解决所有舍入歧义。它们不是 Ascend 融合内核验证，不是模型数据统计，也没有排除利用额外纠正位、其他侧信息或历史重算的编码。若允许用初始模型、完整批次/RNG顺序重算历史，问题还包括其计算和工作内存代价；不能把不同梯度历史的反例说成对这种重算的排除。

### 可继续研究的精确表示

让预测器只使用解码时确实还存在的数据，例如当前W、已保存的另一份状态、步号和确定性元数据。预测得到P后，存储整数残差 `R=bits(state) XOR bits(P)`；解码时做相同预测与XOR，恢复原始FP32位串。预测不准不损害正确性，但会恶化编码大小。解码已依赖的另一份状态、预测元数据、纠正位及原样回退都必须计入；不能用已丢弃的梯度或旧权重作隐含免费输入。这是利用侧信息的联合无损编码，尚无实际状态上的压缩率。

另一个相关方向是[可逆学习：Maclaurin等，ICML 2015](https://proceedings.mlr.press/v37/maclaurin15.html)。作者对带动量SGD反演训练轨迹，并用补充信息处理有限精度丢失；其目的是减少超梯度计算保存的历史，不是证明标准FP32 Adam的当前m/v可以免费删除。不能将其相对整条训练历史的内存收益套用到本任务。跨步积累的补充位也必须计数，不能假定其大小长期不变。

当前结果：找到明确的舍入反例，尚未找到可直接删除一份状态且逐位等价的重建方法。最值得验证的是实际状态在已有W等侧信息下的可预测残差大小，而不是只验证实数公式能否移项。

后续已完成[纠正位容量研究](correction-bit-report.md)：包含可逆区间序号编码、可达状态枚举，以及一个现成公开11M模型FP32 AdamW快照的CPU离线实测。保留u/v时m的纠正流可小至约0.618位/参数，但算入u/v基底后外推仍约165.04 GiB；所测完整表示均未达到30 GiB。所有解码均检查原始uint32位串一致，没有运行训练或NPU任务。
