# Adam 严格 FP32 第六阶段单驻留存储区与有界窗口

2026-10-24，Asia/Shanghai。本阶段是 CPU 对设备驻留布局的仿真，不是在 GPU/NPU 执行，也不使用 CPU/磁盘卸载或运行时外部状态后备。

## 结论

可以在单个固定容量存储区内完成逐位一致的分块 Adam 更新，但本轮收益远小于“静态压缩 17%”的直觉，而且计算代价很大。

- 真实 21,508 参数 MLP 连续 4096 步通过参考状态和权重 SHA256 检查。90% 原始容量的持久存储区可用，但小模型的存储加工作区核算从约 305 KB 上升到约 650 KB，没有实际峰值收益。
- 单独标注的 4,194,304 坐标合成布局测试，16 步通过参考检查。固定存储加后续工作区的 traced 核算从 34,080,228 降为 31,597,910 bytes，低约 7.28%；初次操作的 traced 峰值低约 7.26%。整进程峰值 RSS 仅低约 2.0%。这是小规模 CPU 观测，不是显存测量。
- 大布局的优化器 CPU 时间是已经分块的 FP32 参考的约 118 倍，16 步累计搬移 53.23 GB。原地紧凑布局用时间换空间，但当前实现明显不适合直接推广。
- 85% 原始容量、以及 200.39→30 GiB 对应的 14.9707% 容量，都在真实 MLP 首步被原子拒绝，没有部分更新权重或状态。

因此，这条路线有“少量无损节省能保留到实际有界执行”的证据，没有接近 30 GiB 的证据。不继续把时间花在无休止的存储池搬移优化上。

## 算法与计费

整个压缩状态只保存在一个预分配 bytearray arena 中，其容量初始化后不变。每块先在固定窗口中解码旧 m/v，再按原 FP32 运算顺序更新、byte shuffle + zlib level 6 编码。压缩若不比原始字节短，直接存原始块，并记一个 flag。

每次更新有两遍：

1. 预检遍只计算各块新长度及顺序写回的最大前缀膨胀，不修改 m/v 或权重。所有新长度放在显式计费的 uint32 数组中。
2. 容量足够才进入提交遍。重新计算同一块更新，使用重叠安全的 memmove 在同一 arena 内挪动后缀，写回新块和该块权重。

容量不足时在第一遍结束即停止，旧状态和权重的哈希保持不变。没有分配第二个状态 arena，没有把整组解码 m/v 留在路径内，没有从磁盘读旧状态继续计算。参考文件只有哈希，不包含可供优化器恢复的 FP32 状态。

元数据为每块 4-byte 旧长度、1-byte flag、4-byte 预检新长度，以及全局 32-byte 头。存储区始终紧凑，所以碎片为零；未使用的容量全部计为已保留空间，不当成免费内存。观察到的压缩 payload 小于预留 arena，不等于已释放两者之差。

## 可证明的存储边界与不能冒称的边界

设参数数 N、块长 B、arena 容量 A。显式拥有的数值存储为：

A + 9*ceil(N/B) + 32 bytes。

每块保存的长度不大于该块原始 m/v 的 8 倍坐标数。顺序提交时，任一旧/新混合前缀也不超过完整原始状态。因此 A=8N 对任意可压缩性都足够，这是原始块回退给出的严格存储界；它不保证省持久内存。

A=0.9*8N 是条件容量，不是普遍保证。预检能安全拒绝不能容纳的输入，却不能凭空把它压缩成功。工作数值数组/字节仅与 B 成正比，zlib 工作区与其窗口配置相关；无与 N 同规模的第二份 m/v。

上述是拥有的数据/索引存储界，不是整个 Python 解释器、NumPy 或原生分配器 RSS 的严格字节上界。工作区另作测量。zlib 官方给出的默认压缩和解压工作内存量级分别约 268 KB 和 40 KB，取决于构建；不能把这些原生开销当成不存在。[zlib 官方技术说明](https://zlib.net/zlib_tech.html)

## 公平参考与观测

参考在独立进程运行，也采用相同块长和原地权重写回，没有用整向量临时副本人为抬高 FP32 基线。这个分块参考又与早期独立整向量参考的同一 MLP 检查点完全一致。

下表的“存储加工作区”为 Python 可直接核算的持久数组/bytes 分配，加后续优化器操作的最大 traced 临时分配。初始化 traced 峰值单独记录；没有把已经停止跟踪的旧存储错误地算成零。少量解释器对象及原生分配器的完整总界不能由此断言，故另报告进程 RSS，不宣称这是精确设备峰值。

| 场景 | 方案 | 持久数值保留 bytes | 存储加后续 traced 工作区 bytes | 优化器 CPU 秒 |
|---|---|---:|---:|---:|
| MLP 21508 参数，4096 步，B4096 | 分块 FP32 | 172064 | 304620 | 1.684 |
| 同上 | 90% 单 arena | 154943 | 650452 | 53.808 |
| 合成布局 4194304 坐标，16 步，B16384 | 分块 FP32 | 33554432 | 34080228 | 0.478 |
| 同上 | 90% 单 arena | 30201324 | 31597910 | 56.367 |

大布局包含 2336 bytes 的索引、预检数组和头部。最大 payload 为 28,664,247 bytes，固定 arena 约 30.20 MB；不能只报较小的 payload。最终 payload 为 27,238,579 bytes，也没有自动降低已预留 arena。

大布局进程峰值 RSS：FP32 94,199,808 bytes、压缩 92,286,976 bytes。进程 RSS 包含解释器、模型/梯度输入和历史高水位，不等价于仅 m/v 峰值，也不是 NPU 显存。小 MLP 的已有进程高水位高于本次操作峰值，RSS 增量为零，不能解释为优化器不占内存。

## 失败与功能检查

- MLP 首步所需最大前缀 153038 bytes。85% arena 只有 146254 bytes，目标比例 arena 只有 25759 bytes，均在提交前拒绝。旧权重/状态/步数不变。
- 原始块回退压力：B8、4096 坐标、8 步，共 4096 次原始块写入，全部参考检查通过。含索引后比原始数据更大，不能忽略小块元数据。
- 六种梯度流各 128 步，N257、B64，含最后一个非完整块。共 768 个逐步状态/权重哈希检查全部通过；参考阶段只返回哈希，然后释放完整状态，再执行 arena 阶段。这些功能测试不参与内存基准。
- 任意 32-bit 字模式的原始回退通过逐字节恢复检查，包含可能的特殊 FP32 位模式。
- 真实 MLP 的第 1/2/128/1024/2048/4095/4096 步以及大布局第 1/2/16 步检查 m/v 与权重哈希。没有声称对大布局做了训练质量测试。

## 复现

无新增依赖。所有命令在本目录运行，并设置 OPENBLAS_NUM_THREADS=1、OMP_NUM_THREADS=1。

```bash
python resident_arena.py --impl reference --mode mlp --steps 4096 --block 4096 --out results/mlp_ref_b4096.json
python resident_arena.py --impl arena --mode mlp --steps 4096 --block 4096 --capacity .9 --reference results/mlp_ref_b4096.json --out results/mlp_arena90_b4096.json
python resident_arena.py --impl reference --mode layout --n 4194304 --steps 16 --block 16384 --out results/layout_ref_b16384.json
python resident_arena.py --impl arena --mode layout --n 4194304 --steps 16 --block 16384 --capacity .9 --reference results/layout_ref_b16384.json --out results/layout_arena90_b16384.json
python audit_resident_arena.py
```

其他预算拒绝和回退参数见对应 JSON。`results/functional_audit.json` 保存逐步测试和严格存储公式。`superseded_full_vector_reference.json` 仅保留作运算顺序对照，不作为当前内存基线。
