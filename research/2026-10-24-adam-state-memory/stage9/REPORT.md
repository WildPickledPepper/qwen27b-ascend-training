# Stage 9：原生 C 的精确重算、有限缓存与时间—工作区曲线

## 结论

用自己编写的原生 C、已安装的编译器，排除了“小 P 的 Python 对象开销”这一干扰后，**确实观察到逐位精确的净算法工作区节省**，但只在短时间跨度的玩具任务里，而且并未满足更严格的低于完整原始 w/m/v 载荷的预算。

- 预定 129 个候选：98 个完成，全部 9,636 个原始 uint32 与参考一致；31 个触发预先固定的 2,000,000 次 State 入口上限，未删除、未当成成功。
- P64、T2：无缓存重算计入 1,320 B，普通参考 1,928 B，少 **31.5%**，约 **61.8×** 时间。固定保存 16 个坐标的前一时刻状态，用 1,512 B，约 42.2× 时间。
- P124、T2：无缓存重算 1,560 B，普通参考 2,888 B，少 **46.0%**，约 **91.5×** 时间。保存半个时间片（62 个坐标）需 2,296 B，约 43.4× 时间。
- 645 个严格预算测试（原始完整 w/m/v 的 25%/50%/75%/90%/99%）全部拒绝。最省的候选总包络仍为原始完整载荷的 1.048×。不能把“比实际参考工作区小”说成“已低于原始状态载荷”，更不能说达成 200.39 GiB→30 GiB。
- 更长跨度很快破坏这条短期曲线：P32、T3，无缓存约 1,086×；P64、T3 的无缓存和半片缓存均触发上限。接近完整历史时间片能降低时间，但缓存本身又使工作区高于普通参考。

100× 只是本报告的分析筛选线，不是用户指定的可接受训练时间。计时是 CPU 小程序的描述性测量，不保证其他机器或真实网络表现。

## 协议与实现

目标仍是真正耦合的二次型，H=I+11ᵀ/P；每个梯度按 j=0…P−1 顺序逐项 FP32 乘法、加法，**没有改写成 w+mean 的新算术参考**。权重初值由坐标公式生成；不是把预训练权重偷偷藏在另一个完整副本。

AdamW 参数延续 stage8：β1=.9、β2=.999、epsilon=1e-8、LR=.01、解耦 weight decay=.01。t≤8 的 bias correction 常量由同一 binary64 幂计算后转 FP32，存原始字。强制浮点乘加不融合，编译不使用 fast-math；运行检查 round-to-nearest。P4 的 T6/T8 原生参考还与 NumPy stage8 比较了全部 24 个原始字，完全相同。

DFS 不用 C 递归，而是显式 Frame 栈。每帧 32 B，包含 t/i/j/执行阶段、自己的此前 w/m/v、部分梯度。每个返回 State 为 12 B。重算依赖历史权重本身，不读取梯度/权重历史文件，也没有外生梯度 oracle。

比较三种策略：

1. 无缓存。
2. 容量固定的朴素 LRU。每项 24 B：t、i、age 各 4 B，w/m/v 共 12 B。扫描数组查找和驱逐，成本没有忽略。只保存已完整计算的正时间状态。
3. 固定时间片。保存历史时间 tau 的前 Q 个坐标，值为连续 12Q B；坐标键由前缀隐含，tau/已完成前缀长度在头部。建片也靠精确递归，建片调用、时间、栈和字节均计入。Q<P 才是部分片；Q=P 是完整历史片，明确保留为超原始状态预算的对照。

缓存键 (t,i) 只在一个新建且固定的实验上下文内使用。P、H/初值公式、固定 optimizer/舍入版本共同确定上下文，每次测量均清零整个 arena，绝不跨实验复用。没有 RNG。2M 上限也防止本协议内的 uint32 LRU age 溢出；程序不是接受任意恶意大 CLI 输入的通用服务。

预先写入 protocol.json 的案例：P4/T6,T8；P8/T4,T6,T8；P32/T2,T3；P64/T2,T3；P124/T2。P124/T2 的无缓存调用数在 2M 上限内，用于减少固定开销比例，不根据结果挑选。LRU/时间片容量与时间片位置也全部提前固定。每个参考重复 31 次，每个成功候选 5 次；计时报平均、最小和最大值，所有原始数据保留。

## 全部工作区怎么计

每个算法只有一个动态 arena，且实际保留最终的完整当前权重 **4P B**。这不是“所有全向量都消失”。

- 普通参考：头部，w/m/v 三个 P 长 FP32 数组，以及完整当前梯度 g（4P B）。没有全历史。
- 重算：头部，(T+1) 个显式 Frame，LRU 或固定片，完整输出权重数组。没有另外的全 m/v 或全梯度数组。返回值、计数、缓存年龄、状态、摘要都在头部。
- malloc_usable_size 给出该块的可用容量，再加 16 B 作 glibc 块级 header/填充包络。它不是整个 malloc arena、tcache 或进程 RSS。
- 固定数值常量 K 为 112 B，另加 64 B 处理编译器复制的标量/帧初始化常量池；审阅实际机器码确认额外引用不超过该值。报告格式字符串与机器指令代码不作为 optimizer 状态，但也不宣称整个进程只占表中数百/数千字节。
- 用 -mno-red-zone 编译，避免 GCC .su 在叶函数用 red zone 时漏掉真实局部暂存。最终 .su：transition 128 B，query 64 B，algorithm 96 B，main 384 B。重算最大算法调用链为 288 B，参考为 224 B；**两者再把仍存活的 main 384 B 也计入**，得到 672/608 B 栈包络。不是只取最大单个 frame。
- algorithm 内没有 malloc、pow、文件 I/O 或外部数学 kernel 调用；sqrtss 在机器码中可见。初始化/输出/计时基础设施的 libc 内部栈、进程运行时/共享库、验证捕获数组、stdio 缓冲区不在算法包络内。故这不是整个进程物理内存上界或 GPU/NPU 显存实测。

严格 budget 在计算前检查完整 arena+常量+栈包络；若预算不足，更新尚未开始就拒绝。实际分配后再检查 usable-size 包络，无通过检查后再临时增加第二 arena。operation cap 失败的临时 arena 被丢弃，不交付部分轨迹。

逐字验证另起一个冷启动执行：清零缓存/上下文，额外捕获验证输出，断言冷运行摘要与定时运行一致，再与普通参考文件逐字比较。这些验证文件不是算法输入或状态卸载；其额外 12P 输出和 stdio 内存明确不计为正常算法低内存执行。

| 64,2 | 固定片 Q16,tau1 | 1,512 | 1,928 | 42.2× | 逐位相同 |

朴素 LRU 并不免费或自动更好。例如 P124/T2 的 Q123 LRU 要 4,504 B、约 893× 时间，扫描和驱逐开销很大；固定片的结构性索引更有效。此结论针对这个实现/目标，不是所有 LRU 的普遍性能定理。

上限失败行的 CSV 也会记录“到上限为止耗时/参考耗时”，不能误读成完成训练的时间比。字段 status/complete_exact_bits 清楚区分。

## 严格预算为什么仍然失败

原始完整 w/m/v 只有 12P B，而上述算法还需要输出权重、控制栈和管理空间。最接近的是 P124/T2 无缓存，1,560 B 仍高于原始 1,488 B。因此 645 个小于原始载荷的硬预算没有一个接受。相对完整参考工作区的 31.5%/46.0% 节省和这个失败不矛盾：普通参考自身也有当前梯度、管理和执行开销。

若目标只按 m/v 的 8P 计算，还需要分别对共同的当前权重、额外重算权重/历史等做适当划分，不能把这里的 12P 自动换算成用户的 30 GiB。没有做任何这样的规模外推。

## 复现与后续

```sh
cc -std=c11 -O2 -fno-fast-math -ffp-contract=off -fno-math-errno -mno-red-zone -fstack-usage -Wall -Wextra stage9/frontier.c -lm -o stage9/frontier
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python3 stage9/run_frontier.py
```

代码、完整构建命令、编译器栈表、反汇编、源/二进制哈希、原始 word 文件、129 点曲线、645 点预算筛查均随包。构建使用原本已安装的 cc/gcc，没有安装软件或使用第三方实现。

这个阶段说明精确时间换空间并非空谈，同时也清楚显示有限缓存和跨度的代价。下一步转向真实梯度结构：保存当时旧权重生成的 X/dY 等线性梯度因子，计入全部历史因素、bias 向量和元数据，再按相同 FP32 K 次序重建每步梯度块、按时间重放 moments。这是有有限容量/时间跨度的历史重放，不是固定大小的无损状态编码，也不预先宣称适用于 Qwen。
